# Game traps, measured

Each line is a mistake made while building a browser game, read as **what a person sees** → **why** → **the fix**. Where it says *Measured*, the line says how it was found. Look up the group you're working in before you build that part.

## Rendering and the device

- **The player sees a magnified top-left quarter of the scene and blames the camera** → the canvas was sized with `position: fixed; inset: 0` and the renderer was told not to set its CSS size. A canvas is a replaced element: `inset` does not stretch it, so it shows at its drawing-buffer size, which is 2× the window on a Retina screen → size it explicitly (`width: 100vw; height: 100vh`, or let the renderer set the CSS size), and run every visual drive at the person's pixel ratio and window size. Check that the canvas measures the window. *Measured: five versions showed a quarter of the scene on a Retina laptop while every headless drive at pixel ratio 1 looked right; reproduced headless at ratio 2 with the owner's exact pictures.*
- **You spawn inside your ship and the view is a flat grey wall** → the hull was several overlapping boxes. Back-face culling hides only the box you stand in. A neighbouring box's face inside your room is a front face → put exterior shell meshes on their own camera layer, and turn that layer off for the walking (inside) camera. Keep lofted hulls convex, so a camera inside sees every face from behind. *Measured: the first screenshot was the grey wall and 21/21 checks passed; a centre-ray probe found the bow box 1.5 m from the spawn.*
- **One area of the game drops to a few frames a second** → every interior's point lights stayed in the scene, out of sight (19 lights). three.js evaluates every point light for every lit pixel, seen or not, and changing their number recompiles every material. A boarded hull's outside was also drawn behind its own walls → use a fixed pool of 8 point lights, moved each frame onto the room lights nearest the camera. Rooms record where their lights are and never own a `PointLight`. Hide geometry you are inside of. An alarm recolours existing lamps; it never adds a light. *Measured: software GL went from 2.5 to 8.5 fps on that ship; it was unplayable on the owner's Mac.*
- **Frames run slow on a Retina screen** → you are drawing 4× the pixels → step the pixel ratio down by 0.25 when frames run slow (never below 1) and back up when there is room. Cap it at 2. *Measured: built as part of the same frame-rate fix.*
- **The firing frame rate sinks the longer a fight goes on** → each tracer made a new geometry and never freed it (+10 geometries per 4 s of fire) → share one geometry and dispose the material. *Measured: geometry count in the same fix.*
- **Voxel land looks whole from the side and full of holes from above** → the mesher's in-plane axes u × v pointed inward on the top and bottom faces, so default culling dropped them → make u × v = the face normal on all six faces, and test any new mesher in Node on one block's winding, not by eye. *Measured: holes in screenshots, then a Node test.*
- **The sky shows a faint grid and pinches to a point overhead** → the stars and nebula were painted into one 2048×1024 texture on a sphere. Each texel spanned about three screen pixels, and an equirectangular image pinches at the poles → do what the genre does: compute the sky from direction, bake it to a cube map at infinity (`scene.background`), and draw stars as real points sized in screen pixels. *Measured: read from screenshots.*
- **Software rendering runs at half speed for no visible reason** → `scene.environment` lights every standard material per pixel → put `envMap` on the shiny materials only. *Measured: half the software frame.*
- **The shadow pass costs time for nothing** → scenery outside the shadow camera's box still cast into the shadow map → `castShadow = false` outside the shadow box. *Measured: frame-cost drive.*
- **A stray copy of an object sits at the world origin** → an `InstancedMesh` slot that is never set draws at the origin. It is not hidden → make the count exactly the number used.
- **A dark colour comes out light grey** → `Color.setHSL` works in linear space (lightness 0.2 shows as light grey) → use `setStyle('hsl(…)')`.
- **White walls glow in the bright rooms** → a bloom threshold of 1.0 caught ordinary white surfaces → raise the threshold (1.3 worked). *Measured: once, from screenshots.*
- **A face washes out white while a spell charges** → a charge light added on top of a lit face → add less light (+0.35 worked), and grow a projectile's light from nothing over the first third of its flight.
- **Mist draws as hard white squares, and light beams look like sheets of paper** → a bare `PointsMaterial` with no soft sprite, and a flat additive cone → use a soft round point texture, and fade the beam along its length. *Measured: read from the screenshots.*
- **Glow sprites that overlap turn white, and a check that only reads their kind passes** → additive blending clips to white → check the hue on screen at that pixel, not the object's kind.
- **A held model drawn with `depthTest: false` (so it never sinks into walls) shows its own back faces** → with no depth test, its own faces draw in any order → keep depth testing and compress the model's depth in `onBeforeCompile` instead. Or draw the viewmodel in its own render pass.
- **A view fitted to a small screen shows only sky** → to fit the whole field into a small band, the camera stood about 120 units back, beyond where the fog began → start the fog beyond what the view looks at, and never let a fit place the camera inside the scene. *Measured: the drive caught it before the owner did.*
- **Water shows white blotches, and a metal mirror reflects black** → both reflect the room light → give water its own painted sky (`envMap`). A painted reflection reads as a mirror.
- **A shadow-type warning, then hard shadows** → three r186 has no `PCFSoftShadowMap` and falls back with a warning → use `PCFShadowMap` with `shadow.radius`.
- **A mirror floor costs a sixth of the frame** → a `Reflector` at 1024² → halve it (512²) and cut it first on a weak device. *Measured: on an M1, 13.2 ms frame with the mirror at about 2 ms, 4.3 ms at 1024²; never measured on the tablet.*
- **Many skinned people cost far more than their triangles suggest** → `SkeletonUtils.clone` gives every skinned mesh its own `Skeleton`, even when the source shared one (13 per avatar clone), and each is updated and uploaded every frame → re-share the skeleton after cloning. *Measured: on the tablet.*

## Time and the game loop

- **Game time runs at half speed on a slow renderer** → the frame dt was clamped at 0.05 s while software GL drew about 8 fps → clamp dt at 0.1, so game time keeps up with the clock down to 10 fps. *Measured: once, in the first session's drives.*
- **After a cutscene the player is standing in space 27 m behind the ship they boarded** → the timeline fired every event that was due, then ran every track. On one slow frame that crossed both, "sit in the seat" ran first, and then the climb's last step placed the body in the old frame → run tracks up to each event's time before firing it (strict time order). Check the distance from the seat, not only the phase. *Measured: every check green; only one screenshot showed it.*
- **A spring (camera, rope) overshoots and explodes on a slow machine** → it was integrated with the whole frame's dt (headless ran at 3 fps) → substep it.
- **A timer takes 20× too long on a slow machine** → it counted frames (`t -= 1/60`) → use wall time or dt.
- **The fps counter says 20 while the game really runs at 9** → fps was computed from the clamped dt, so it can never read below 1/clamp → compute fps from unclamped wall time. *Measured: once.*
- **An effect started inside another effect's callback never ends, and its sprites stay in the room for good** → `update` filtered the live list in place, so a callback that added an effect lost it → swap in a fresh list before running the callbacks, and keep whatever they start. Check by counting scene objects before and after.
- **Enemies chase you and almost never bite** → a sensor running every 0.25 s put the state back to `chase` whenever it saw you, which cancelled the 0.32 s attack → mid-action, a sensor changes only the target, never the state. *Measured: 28 s of chasing, the attack state lasted one frame, no bite.*
- **Two needs at the floor flip-flop forever** → each cancelled the other every frame → handle one at a time.
- **An intermittent "the action doesn't start"** → a teleport kept the old velocity, and the leftover momentum triggered a different action → zero velocity on teleport.
- **An enemy can never lose you while it is blind** → the chase tracked your real position → chase your last seen position.
- **A fighter cannot hold still at an airlock** → the flight model had a minimum speed → allow 0 and latch the craft on once the hack starts. *Measured: once.*
- **The autopilot creeps the last few hundred metres** → a proportional throttle never arrives → fly a braking curve. *Measured: 700 m to the dock took 54.7 s before the fix and 15.3 s after.*
- **Inside a synchronous "advance n steps" loop, an arrival never happens** → `await` on a promise that has already resolved still defers to the end of the loop → keep the path synchronous.
- **A baked one-shot animation ends on its first pose (sitting down ends standing)** → the clip was sampled with a looping action, and `mixer.setTime(duration)` wraps to 0 → sample with `LoopOnce` + `clampWhenFinished`.

## Driving it headless, and screenshots

- **Every 3D page shows "No WebGL here" to an agent's headless browser** → the launcher passed `--disable-gpu` alone, so `getContext('webgl')` was null → add `--use-angle=swiftshader --enable-unsafe-swiftshader` (software GL). *Measured: `{gl:false}` before, `{gl:true, meshes:"12"}` after.*
- **A 400 ms key hold moves the player almost nowhere** → headless Chrome starves `requestAnimationFrame` (about 2.5 frames in 400 ms) → gate on game state (`waitFor`), never on wall time. *Measured: once.*
- **A drive waits a minute and the music, the next wave or the end of the workday never comes** → software GL draws 2–8 fps and the game steps at most dt-clamp per frame, so headless game time runs at a fraction of real time (one shooter: 15 % without a looser cap) → give the page hooks: `fastForward(seconds)` (logic only), a `?dtmax=` URL setting, `advance(n)`, and then count frames. Read speeds from the game (`hero.speed`), never a stopwatch. *Measured: a dance game with dt capped at 0.05; a shooter at 2–3 fps; a life sim at about 4 fps, where a headless workday took 4 min one run and timed out the next.*
- **All checks pass on a picture of the wrong thing** → state counters (`stats()`: phase, position, credits) cannot see a wall in your face → look at every screenshot, and gate "what do I see" on a centre-ray read through the camera's own layers. *Measured: 21/21 green on a grey wall; three more view defects only screenshots showed: a nose at eye level, a prow filling the view, a copied sky with a battle station in it.*
- **A "something within 3 m" check passes on an empty view** → the ray read reports a miss as `dist: Infinity`, JSON sends that as `null`, and `null < 3` is true → ask `typeof d === 'number' && d < 3`. *Measured: the first such check passed on the broken code.*
- **No shot ever landed, and the check was green** → the check said `after < before || before === 60`, and a fresh target has 60 hp, so a miss passed → run every new check once against the old code and see it fail. *Measured: green on a shot that never hit.*
- **"All drives green" meant nothing** → the drive tool printed values and always exited 0, and a timed-out wait printed and carried on → give each eval step an `expect`, make a timed-out `waitFor` a FAIL, and exit 1 on any FAIL. *Measured: the next drive would have passed a real defect.*
- **Score is 5 before a key is pressed, and two goal checks pass on top of it** → all the coins started under the player. The goal checks ("score ≥ 3", "every coin moved") were true at once → assert the start state beside the goal. *Measured: only the start-state check failed.*
- **A toast never appears in screenshots** → the toast lasted 3.5 s of real time and a software-GL screenshot took longer → log toasts with a `MutationObserver` into a page array. Read it in the *next* step (it is empty in the same eval that caused it). Right after `advance()`, nothing is drawn yet.
- **A page in a hidden window or a background tab never updates (an empty `<body>`, no error)** → rAF does not fire in a hidden window, and a tab that is not in front draws nothing → `Page.bringToFront` on that tab's own connection, plus `Page.setWebLifecycleState {state:'active'}` and `Emulation.setFocusEmulationEnabled` on the same connection. Coalesce writes on a timer, not on rAF. *Measured: in an editor window and in multi-tab headless Chrome.*
- **A drive's trigger press does nothing** → a 40 ms release never reaches a 300 ms headless frame → hold until a `waitFor` sees the shot.
- **A one-frame effect (a muzzle flash) cannot be photographed** → at 3 fps it is gone between frames → set the page's `dtMax` to 0.002 before firing, so time almost stops.
- **The second eval step throws SyntaxError** → evals share the page's global scope, so a second `const p` collides → wrap each eval in `{ }`.
- **Checks flake after an input followed by a fixed wait** → headless frames are irregular, and a shader compile can hold one for seconds → `waitFor` the state.
- **One test's leftover enemy kills the player in the next test** → drive scenarios leak → park everything at the start of each scenario (alive = false, hidden) and wake only what it needs.
- **Every real-time check goes red while the behaviour is fine** → the machine was loaded (load 16–22 from other headless runs). With dt capped, game time slows and real-time windows miss → one drive at a time, `nice -n 19`. Check the load (`ps -r`) before reading a red, and rerun a known-good build as a control. *Measured: every real-time window red, while state-gated suites stayed green.*
- **A throttled CPU and Chrome's memory don't stand in for a weak device** → `Emulation.setCPUThrottlingRate` barely moved main-thread ms for a rAF page (the page busy-waited instead), and Chrome RSS on macOS falls during a run (compression) → measure on the real device. For memory, use `HeapProfiler.collectGarbage` + `Runtime.getHeapUsage`, plus texture arithmetic for the GPU.
- **A synthetic `PointerEvent` on the canvas throws in OrbitControls (`setPointerCapture`)** → the error comes from the check, not the game → use CDP `Input.dispatchMouseEvent`/touch events.
- **The drive cannot test mouse-look** → headless Chrome grants no pointer lock → add an `?auto=1` start that skips the title and the lock, and let the drive write the input object directly (`driven = true` stops the keyboard reader overwriting it).
- **A rule tied to real time changes the outcome under a slow drive** → timed answers were all "instant", so every answer scored the ×1.5 bonus → give drives a URL switch (`?timer=off`), and pin seeds and random picks in every check URL.
- **A check that builds on generated terrain fails on the terrain** → test rigs collided with the world (and a new cave started inside the base) → build rigs in a known clear spot. Then check what the game's own environment tests read there: a "under open sky" test scanned from the generator's top, so a rig in the sky read as open sky.
- **A hand-over (landing, cutscene end) leaves the player facing a wall, out of reach of the next action, and every state check passes** → nobody looked at the first frame the person gets back → screenshot that first frame and check the reach to the next use point. *Measured: 1.5 m from a flank and 4.5 m from the use point.*

## Input and phone controls

- **On the phone, a tap or a "hold still" on the look area almost never counts** → a real thumb drifts past the still threshold, and a slow frame stretches a tap past the time limit → every action gets a button. The look half does nothing but look. *Measured: the owner on an iPhone; the drive's "quick tap" check was green the whole time.*
- **The thumb hunts for the right button** → buttons moved with the item in hand → buttons change their label, never their place: one big button and one small, plus Jump fixed at the bottom right. Decide the action on touch-down and keep it until touch-up.
- **Walking into a one-block step hops short of it** → auto-jump at 0.8 of a jump peaked below the block → no auto-jump; a fixed Jump button.
- **The fire and aim buttons vanish while aiming** → a full-screen scope overlay was added after the buttons and painted over them. They still worked, so nothing in the code looked wrong → give controls their own layer above every overlay. Check painted order: make the overlay hittable for one read, hit-test the button's centre (`elementFromPoint` skips `pointer-events: none` layers), and as a control in the same read lower the button and expect the overlay. *Measured: only a picture showed it.*
- **Holding Dig freezes the view, so clearing a wall is lift-look-press for every block** → a held button did not steer → while a button is held, dragging turns the view at the look-half's speed. Touch moves keep going to the element first touched.
- **Buttons fire once, or the look area steals the touch** → act on `touchstart`, release on `touchend`, with `preventDefault` + `stopPropagation`. Turn off the browser's own touch handling: `touch-action: none`, `user-select: none`, `-webkit-touch-callout: none`, `user-scalable=no`. A manifest with `"display": "fullscreen"`, `"orientation": "landscape"`. Show a "turn your phone sideways" card in portrait.
- **The phone stutters** → draw distance set for a desktop → make it a phone setting (3 chunks against 4).
- **Under load, a drive's tap reads as a hold** → headless runs at about 3 fps and CDP round trips stretched a tap past 260 ms (the game's tap limit was 320) → gate drives on outcomes (`waitFor`).
- **W walks backwards or sideways whenever you face anything but fore or aft** → both `sin` terms in the yaw rotation had flipped signs. At 0° and 180° sin is 0, and the drives only walked along the corridor → test W/A/S/D at eight headings against the camera's own forward and right (32 dot products, worst > 0.99).
- **"Forward" runs the character at the camera after a fixed view hands back control** → forward came from where the follow camera was *going*, while the drawn camera eased there over her head → read forward from the drawn camera, and keep the camera on the side it is already on. *Measured: 16/16 at a fixed-view hand-back and 0/72 from a settled camera, then 0/16 after the fix.*
- **The owner calls the camera "maddening" and gets nauseous** → a free orbit camera, a title that spins, a turntable, a camera that glides between views → copy the genre: tower defence keeps one fixed angle with pan and zoom, or offers a few preset views. A change of view is a cut, and nothing moves by itself. *Measured: three rejections and a whole session; v6 "finally usable".*
- **…but the rule above, worded as "a change of view is a cut", cost a game its free zoom** → the rule was read as forbidding the person's own wheel zoom → the person's own drag or zoom may move and ease the camera. Only motion *by itself* is out. *Measured: the agent given the rule built two fixed zooms, while the one without it built free zoom and was preferred.*
- **The person clicks a 3D shape and the panel is empty** → the click selected the bare child mesh, not the object it belongs to → a click selects the object the person thinks they pointed at (the parent), with a modifier for the bare part. *Measured: the owner called it "a major brain breaking point".*

## Models, frames and assets

- **You walk through crates and pillars inside a moving ship** → `Box3.setFromObject` measures in world space, and the result was stored as a ship-frame collider → measure each mesh through the host frame's inverse matrix. *Measured: colliders were off aboard two ships and a station.*
- **No shot ever lands aboard, and enemies see through walls** → ship-frame points went straight into a `Raycaster`, which tests the world → cast the ray out through the host's matrix and bring the hit back into the host's frame.
- **Cloned VRM avatars hold their arms half up** → three-vrm runs twist constraints on the original only → rebuild the constraints per clone from `nodeConstraintManager`. A clone also inherits what the original wore (strip it), and its materials are new objects (key dyes by material *name*).
- **A newly spawned body has a huge head or a frozen root** → it was cloned from the first *live* body, which carried headshot scaling → clone from a rest-pose template, never from a body in play.
- **A 20 cm pistol in the hand comes out 3 mm long** → the hand bone lives in the rig's units (cm scaled to m above it) → undo the hand's world scale on the mount, and read bone axes (Rocketbox: +X fingers, +Y out of palm, +Z thumb) before placing props. Hang a world-placed prop with `bone.attach` after `updateMatrixWorld(true)`. *Measured: a probe showed `gunAt == handAt`.*
- **An asset named "Police_Female_01" is a masked man in riot gear** → asset names are not their contents → look at a picture of every asset before using it. Props (guns, helmets) can be material groups inside the body mesh.
- **A person converted from FBX is 10.5 MB** → unindexed, with 175 full-body morph shapes and 14 pieces from material runs → weld, mix the shapes down (6), regroup by material, and store expressions sparse (eps 1e-3; the FBX's cm noise defeats 1e-6). Result: about 1.1 MB. Also: FBXLoader `userData` becomes 170 KB of glTF extras per clip; Rocketbox FBX diffuse comes in black.
- **A mocap walk still slides the character forward** → root motion is baked into the clip → strip it and use it as the speed. Clip paces can be slower than the game's (0.95/1.8/2.05 m/s), so cap `timeScale` rather than leave walking "painfully slow".
- **One part's bounding box is the whole body** → the parts share one vertex buffer → size from bones. GLB textures are stored flipped, so read pixels through the UVs.
- **Missing clips** → some free rigs lack crouch, eat or kiss clips (Rocketbox men have no crouch_in/out) → pick clips from a fallback list, compose from parts of other clips, or lean a bone after the mixer runs. Quaternius rigs hang the legs off `Root`, not the hips.
- **A texture count reads 0 on VRM models** → MToon keeps its textures in `uniforms` → read them there. Public IPFS gateways answered 429; a pinning gateway worked.
- **200 animated people won't fit a weak tablet** → core three.js has no skinned `InstancedMesh`/`BatchedMesh`, and CPU skinning costs about 0.8 ms a person (12 skinned = 9–10 ms on the tablet, so 200 ≈ 160 ms) → for a fixed camera, bake sprites from the 3D models ahead of time and draw the crowd as one instanced draw call. Gear goes in layers (one row per piece, depth-masked), not a sheet per loadout. Keep the few close-up characters skinned. Bake on the build machine, not the device. *Measured: tablet numbers for 12; 19 people from four libraries flattened and matched their 3D selves.*
- **Free model packs: what the licence and weight really are (checked in October 2026; check again before you ship)** → Kenney: CC0. KayKit Adventurers: CC0, with hand sockets for its 25 weapons. Quaternius Modular/Universal Base: CC0, but the Ultimate Animated Character Pack is free and *not* CC0 or redistributable alone. Microsoft Rocketbox: MIT. Polygonal Mind 100 Avatars: CC0. Open Source Avatars VRM: per collection (CC0; VIPE is CC-BY). Ready Player Me shut down on 2026-01-31. Free, no-login "heavy" characters top out at about 20k triangles; the heavy ones are heavy in textures (VRM 43–85 MB). No free MIT/CC0 survivor characters were found. A sandboxed page (an artifact) cannot load assets from a pack's site, so ship them or draw them.

## Audio

- **Recorded music would chipmunk or drift out of step** → the game plays dances at 4 counts a second (about 2.5× real time) and at ×2 → synthesise the music on the game's counts (Web Audio), so it stays in step at every speed, skips cleanly, and ends on the home chord exactly where the engine ends. Silent above ×2.
- **You can't check levels by ear in a drive** → a drive has no ears → render the mix offline (`OfflineAudioContext`) and measure the levels. When choosing sound files, measure onset, peak and spectral centroid (ffmpeg `aspectralstats`), and then *ask the person how they land*. Sounds in a cutscene have never been heard by anyone until the person plays it.
- **A sustained tool sound annoys the ears** → it sat at 2.5 kHz → keep sustained voices out of 2–5 kHz. *Measured: the owner's verdict on the first version.*

## The page around the game

- **The side panel prints the word "null"** → `Element.replaceChildren` writes a `null` argument as the text "null", and the section builders returned `cond ? el : null` → `.filter(Boolean)` first.
- **A hidden overlay still shows, or still eats every click** → a stylesheet `display: grid`/`flex` beats the `[hidden]` attribute → `[hidden] { display: none !important }`. *Measured: twice: six screenshots of a loading overlay over a running game, and an editor overlay that took every click.*
- **A fully faded-out spinner keeps the GPU busy forever** → `opacity: 0` and `visibility: hidden` do not stop a CSS animation; only `display: none` or removal does → set `display: none` after the fade, and find running animations with `document.getAnimations()`. *Measured: GPU process 0.92 % → 0.03 % of a core, renderer 1.42 % → 0.04 %.*
- **Adding `&x=none` to a test URL did nothing** → `URLSearchParams.get` returns the *first* value → replace the param, never append. And a random pick for one thing must not draw from the seeded dice, or every other seeded choice moves.
