# The Id-bind drive (P18 session 114, 2026-10-16)

P18-S113-IDBINDREAD: a Record whose Fetch is unwired. In the running app its Id only binds it to the app's copy of the
record (`setModelID`, `Model.get(id)`): no request, no Done, no Error. EXP-011 §43 had exported it as a read on every
Id change. s113's run 1 found that, on this same graph.

`bind-desk` (generated by `gen-bind-desk.py` from s113's generator: record-desk with the Load button and its two Fetch
wires removed) has two Records on one Id, **Shown** ("Record properties" unstated, so ticked) and **Frozen**
(unticked), and s113's `Rename` form. One real `nodegx-backend` from `src` on :8594, one `Page` seeded `Home`, three
arms in one headless Chrome. `EXPECTED.md` was written before the run.

## Running it again

From this folder: `python3 -I gen-bind-desk.py`, then `./build.sh --emit-fixed` (emits the fixed arm from the working
tree and bundles both arms with esbuild), then `node drive.cjs`. `out-control` is not rebuilt by the script: it was
emitted once by `emit.ts` with HEAD's `plan.ts`, `component.ts` and `emitApp.ts` put back for that one emit, then
restored and `cmp`-checked. `drive.cjs` starts the backend, `scripts/devtools/render-from-disk.js` (the runtime arm,
whose viewer bundle was built 07:19 today, newer than every runtime commit; the one uncommitted runtime edit in the tree
is a peer's Upload File header change) and Chrome (`--use-mock-keychain`, a free CDP port), and stops all three when it
ends. `bind-desk/`, `out-*/`, `seeded-id.txt` and `drive.log` are generated and not committed.
