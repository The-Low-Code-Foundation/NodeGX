## 5. Findings

**Missing in the product** (each pushed logic into a script):

1. **No translation or word-table node.**
   - 28 Functions paste `WORD_HELPER` (`wordMap` over rows `{key, en, fr}`, filling `{b}` with the robot's name; cg003Scripts.ts:87-97).
   - `Logic/Translate words` (cg003Scripts.ts:896) is a Function with **~650 output ports**, placed **16×**. `Logic/Hint table` is the same pattern with 29 ports.
   - An Object node over a per-language object would give the ports natively (modelnode2.ts:451-468). Nothing native fills `{b}` across a table.
   - *(Grep of the node catalog for translat/i18n/locali/language: no such node.)*
2. **String Format fills a repeated placeholder once, and its ports come only from the authored format** (stringformat.ts:53, 92-93, 133-136). The template's universal `fill(text, vars)` is a split/join (replace every occurrence, keys arriving on a wire), so it cannot be String Format.
3. **Array Filter has eq / neq / gt / lt / gte / lte / regex only** (filtercollectionnode.ts:22, 46-62). It has no "in list" or "not in list", no nested path (`item[key]` only) and no computed field. This blocks Island pins (`done.indexOf(id) === -1`), Pad keys (key in allowed list), Pick thing (`floor(x)`, kind not in SKIP), Plot at (`x < c.x + c.w`) and Olive held.
4. **No native node edits a nested JSON value**: push to a plain array, set a path, insert into a tree.
   - The Array nodes act on id'd Noodl records (Insert Object Into Array takes `collectionId` and `modifyId`, per the catalog).
   - The whole save is one nested JSON "family model". So every save mutation is a Function (Add profile, Update profile, Update robot, Select profile, Bring home, Complete request, Buy, Island keep). The program tree edits are Functions too (Accept proposal, Fold, Unfold, Card gate, Win summary, Read program).
5. **Repeater rows are global Noodl Objects by id.** Twin or nested lists collide, so the scripts mint prefixed row ids. Evidence: cg003Scripts.ts:356, 999, 1091, 1298, 1490; cg002Scripts.ts:2370; iw006Shop.ts:46; iw006Owed.ts:40. It is what keeps Robot cards (nested ability/paint/hat lists per card) from being nested Repeaters with row components. Related to D57/GAM-005.
6. **Kit ports take whole JSON view-models**, for example garden-kit's `palette` is `type: 'object'` (templates/bot-garden/noodl_modules/garden-kit/index.js:2672). So Draw world (a per-thing switch over ~20 kinds), Kit palette (nested slot options) and Palette exist only to build one JSON value. The graph cannot compose a kit's content. Array Map, the nearest native node, is itself a script (`mapScript`, mapcollectionnode.ts:117).
7. **No "join a list into text" node** (Gift line, Var monitor, Olive held's text, Crew chips' `hereText`). It is only possible with an Expression or Array Map script.
8. **No base64 / codec node** (Encode / Decode save code). The Hash node encodes a digest only.
9. **Scroll into view.** Find robots is a DOM script (`querySelector`/`scrollIntoView`). ISL-009 ruled 10-02 "Signal on every node", not built yet. That is its owner.
10. **Ports are mined from text** (cg002Scripts.ts:26-31). This is why Translate words is one line per word, 30,951 of its 31,220 own bytes being `Outputs.x = …` lines. ISL-006 owns it.

**Teaching / the agent did not use what exists** (all native and present, with the ports checked in source):

11. **Expression**: 0 in the template. The catalog itself says "Prefer Expression for simple pure computations" (docs/node-catalog/enrichment/javascriptfunction.json:5). 22 of the 88 Functions are Expression-sized (Brain size, Glow, Run cap, Card seen, With ghost, Olive played, Voice hint, Challenge, Tidy line, Renderer, …).
12. **Object (Model2) accepts a plain JS object and lists its properties as output ports** (modelnode2.ts:259-260, 451-468): 0 used. **50,881 bytes** of own logic are `Outputs.x = obj.x`-style unpacking lines. Caveat: each new plain object becomes a new global Object; the memory cost is not measured.
13. **HTTP Request**: method, `header-`/`body-` ports, timeout (httpnode.ts:425-460). 0 used. 4 Functions hand-roll `fetch` with an AbortController: Ask Olive, Olive lesson, Olive status, Try Olive. **Run Tasks** (a component per item, async) could carry Olive lesson's per-question loop: 0 used.
14. **Array Filter → `firstItemId` → Object** gives a native "look up a row by key". It is unused, while 18 Functions find a row by id in a hand-written loop such as `for (…) if (reqs[i].id === id) req = reqs[i]` (regex over own logic).
15. **The Function node's docs contradict themselves and the code.** `ports.run` says "When connected, input changes no longer auto-run the script" (javascriptfunction.json:8). The description says connecting Run "takes nothing away". The code (simplejavascript.ts:617-627, NDA-017) agrees with the description, so `ports.run` is stale.
16. **The template still works round ISL-002** (cg003Scripts.ts:392: "a States node's first-state false never arrives"). ISL-002 was fixed in `06e65ab47`, so the workaround and its comment are now stale.

**Process / incentive:**

17. **The generator's gate grades a Function's text in plain Node.** `runScript` (`new Function('Inputs','Outputs', script)`, cg002Scripts.ts:2532-2543) and `helper()` (:2555) do it. The stated pattern is "one source, one gate, one generator. Every script ships in a named `Logic/*` component" (cg002Scripts.ts:7-9).
    - There is no equally cheap way in those tests to grade a native graph. The runtime has a node-level harness (packages/noodl-runtime/test/helpers/node-harness.ts:80 `createGraph`) that the template gates do not use.
    - So the cheapest testable unit is a script, and every behaviour became one. This is the strongest single reason the island is 88 Functions.
18. **The generator pastes whole blocks.** Functions that reach 5–15 % of `ENGINE` carry all 95 KB (§4). This is a generator habit, not a product limit: it inflates the 1.9 MB.
19. **The scope grew 31 % since 10-01** (83→88 Functions, 17→20 engine copies, `ENGINE` 75.8 KB→95 KB, 91→108 helpers). The task file's numbers are already stale.

## 6. For the plain-words question to Richard

The island has 88 Functions holding 3.2 MB, and **93 % of that is shared code pasted in again and again**: about 209 KB of library, copied up to 28 times. Each Function's own job is small: 223 KB in all. When each job is sorted:

- **About a third (26 Functions) could be ordinary NodeGX nodes today.** States, Conditions, Static Data, Array Filter, Object, HTTP Request, Repeaters, and above all the Expression node, which the template never uses once. Three of them wait on a missing piece: a word-table/translation node, and an "in list" filter.
- **Another third (33) fit your "logic component" idea exactly.** Each asks the shared code one question with one answer: "take one step", "run to the end", "is the goal met", "how full is the job", "read the family save", "assign this robot". Put the engine in one component and place it where it is needed, and the engine goes from 20 copies to 1 for these.
- **The last third (29) is genuinely code**: the save-code format, tree edits on the child's program, the grid of the island. Only **15** of them need shared code partway through, calling the engine or the save helpers inside a loop. Those 15 are what a component cannot hold.

So the shared code that only a script can hold:
- **15 Functions** still need it: about **1.0 MB** of copies, against 3.0 MB today.
- **6 engine copies remain, not 20**: Island world, Win pay, Record step, Use helper, Land card, Shop card.
- The question for Richard is whether those 15 are enough to justify a shared-script file (ISL-005's original recommendation), or whether they should be folded into the engine component as extra ops.
- Either way, the first ~59 % of the saving needs no new feature. It needs native nodes and components used as Richard described, plus the four product gaps above: translation table, String Format replace-all, "in list" filtering and the global-by-id rows.
