JSON never turns into HTML

JSON turns into JavaScript objects. Some of those objects then keep a piece of HTML up to date, for as long as the page is open.

That is the whole trick. The three layers above are three different things that exist at the same time once the page is running. Each appears at a different moment during start-up.

JSON

The blueprint

What the editor writes when you deploy. A list of components, each with its nodes, their settings, and the wires between them. It describes the app; it does nothing by itself.

Arrives
Inside the page, as window.projectData. A large app fetches extra parts later from noodl_bundles/…json.
Read
Once at start-up, into models (ComponentModel, NodeModel).
Kept?
Yes, as models. The runtime goes back to them to build a Repeater row or a new page, and to apply an edit from the editor.
JavaScript

The engine

One live object per node, made from the node library’s definition for that type. Each one has inputs, outputs, and code that runs when an input changes. This is the part that “runs”.

Built
At start-up, by NodeScope.setComponentModel.
Runs
In frames. A change marks nodes dirty, then the next animation frame updates them.
Logic nodes
Live only here. A Counter or an HTTP Request never becomes HTML.
HTML & CSS

The page

Only visual nodes reach this layer. Each one hands React a description of its element, and React creates the real elements once. After that, nodes change what is already there.

Created
When React first commits the tree. That is the first moment any HTML exists.
A style changes
The node patches element.style directly (setStyle).
Text changes
The node asks React to re-render it at the end of the frame (forceUpdate).

Where phase 107 comes in

The engine on this page is one way to run a graph. It isn’t the only one, and every one of them has to know exactly what each node does:

The runtimeWhat this page shows: the JSON goes to the browser and node objects run it.
Code exportPhase 18 turns the same graph into React source code ahead of time. The browser gets no JSON and no node objects.
The editorDraws each node’s ports, names, defaults and descriptions.
AgentsLearn what a node does from get_node_type over MCP.

Each of these used to carry its own copy of “what Counter does”, and the copies drifted apart. Phase 107 writes each node down once, as a small spec. A spec is a set of pure functions: given the node’s state, its inputs and what just happened, it says what changes, what fires, and how it went (Done, Unchanged or Failed). A conformance runner then plays the same scenarios against every implementation and compares what each one did, event by event. It also plants bugs on purpose (mutants) to prove every check can actually fail.

Select the Counter on the engine board (“Slide index”), open Its spec, and run a small version of that check yourself. Then plant a bug and watch both the check and the carousel go wrong.

Progress on 3 October 2026: 102 of 147 picker nodes conform on the runtime.

The runner keeps finding behaviour that no existing test ever checked, for example:

  • The Object node’s “<property> Changed” signals have never fired.
  • HTTP Request’s authentication presets have never sent a credential.
  • Giving String Format’s Format input something that isn’t text stops the node for good.

How this page is built: the engine here is a small model of NodeGX’s runtime, written for this page. The method names in the narration are the real ones, from noodl-runtime and noodl-viewer-react. This page writes the DOM directly where NodeGX goes through React, and it runs every step in one queue where NodeGX batches changes into animation frames. Node ids are shortened; real ones are long random strings. The JSON follows the exported format (sourceId / sourcePort), trimmed to the parts that matter here. Nothing in the contact form leaves your browser.
