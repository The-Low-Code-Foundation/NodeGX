## 1. How the game works today

### What it is

**Le Gala de danse** is a management game in French and English. The player runs a dance school and gets its end-of-year
gala ready. They set the running order (`Tabs/Order`), choreograph each number on a stage plan seen from above
(`Tabs/Formation`), and choose costumes and hairdos (`Tabs/Costumes`), the snack before the show (`Tabs/Gouter`), the
dressing-room furniture (`Tabs/Build`) and, from season 2, the car park (`Tabs/Parking`). Things are bought with stars
in the shop (`Tabs/Shop`). There is a general rehearsal, then the gala night itself. The evening plays out in a 3D school
built with three.js, and the game then shows verdicts with a "Why?" for each one (`Game/Results`). A gala night earns
stars and adds an entry to the school's notebook (`Tabs/Notebook`). "Next season" adds new classes.

### How it is put together

- **It is a NodeGX app** in `app/`, with runtime react19 and project format 5. The graph is 54 components with 762
  nodes, stored as JSON under `app/components/`. I read it through
  `npx -y @nodegx/mcp@0.2.4 app --graph`, as `CLAUDE.md` says to.
- **Most of the game's logic is plain JavaScript** in `app/scripts/`. Graph Function nodes call it through
  `Scripts.<name>`, and the files load each other with `use('…')`:
  - `rules/*`: the game's rules: the data tables, `engine.js` (`simulate()`, the evening as a pure function) and
    `plan.js`. These files are **generated** from `gala-rules/src` by `tools/sync-rules.mjs`, so they must not be
    edited by hand. `tools/check-rules.mjs` checks that the copy plays the same evenings.
  - `stage/*`: the 3D scene and the music. They are generated by `tools/sync-stage.mjs` from a `reference/src` folder
    that **is not in this folder**.
  - `game/actions.js`: what each press does to the save. These are pure functions that return `{ save, ui, toast }`.
  - `game/dispatch.js`: turns one press (`act`, `arg`) into the right action.
  - `game/save.js`: the save's shape. `fresh()`, `mend()` (repairs an old save) and `nextSeason()`.
  - `game/text.js`: fills in the words.
  - `view/*`: what each panel shows.
  - `settings/*`: the grown-ups' checker and how their changes are laid over the game's tables.
- **One event bus.** Every button sends the event `gala-act` with `act` and `arg`. Exactly one component,
  `/Game/Dispatcher`, listens. Its Function `dp_fn` calls `Scripts.dispatch.dispatch(...)` and writes the answer into
  the Global Stores.
- **Two Global Stores** are created in `/Logic/Start Up`:
  - `gala` (node `su_gala`): `persist: true`, `storageKey: "gala-game-v2"`. **This is the whole save**, under the key
    `save`. It is kept in this browser's localStorage and nowhere else. About ten components subscribe to `gala.save`
    (Top Bar, Camera Bar, Sheet, every tab, Season Letter, the Grown-ups page and others).
  - `ui` (node `su_ui`): not persisted. It holds what is on screen: the tab, the live evening (`live`), its result
    (`res`), the camera and the toast.
- **Two pages** sit under the Router in `/App`: `/Pages/Game` (the start page) and `/Pages/Grownups`.

### The save (what "progress" means)

The save comes from `game/save.js` `fresh()` and is one JSON object, roughly
`{ v: 2, lang, season, galaDone, seenIntro, plan: {…running order, every number's blocks/steps/formation, costumes,
hair, snack, cake, parking, backdrop}, school: { name, stars, earned, owned: {…}, upgrades: {…}, furniture: […],
logeCols }, notebook: [ {season, at, points, satisfaction, nums} ], sound, seed }`. Every press replaces it as a whole.
`dp_fn` emits a new `save`, and `dp_setSave` writes it to the `gala` store, which writes it to localStorage at once.
**Progress is therefore already saved locally on every press.**

Some details matter for this feature:

- **A gala night commits only at its end.** `dispatch.js` handles `case 'runDone'` by calling
  `actions.js` `finishGala()`, which sets `galaDone`, adds the stars and adds a notebook entry. While the evening plays,
  the run lives in the `ui` store only. If the page closes mid-evening, the gala was not played and can be played
  again.
- **Replaying gives the same evening.** The gala uses the season's `save.seed` (`stage/play.js` line ~114 calls
  `simulate(... seed: G.S.seed)`).
- **"Start again"** (`Tabs/Notebook` → `note:resetYes`) replaces the save with `fresh()`.
- **"Next season"** (`go:nextSeason`) calls `save.nextSeason()`.
- **The save also holds `lang` and `sound`.** These are per-player settings, which is what we want.

### Start-up (`/Logic/Start Up`), in detail

This is the part the feature changes most:

1. `su_words` loads every word (Static Data) into the Variable `words`.
2. `su_gala` loads the persisted store. When it is `ready`, it switches `su_storeReady` on and starts `su_wait`, a
   4-second timer.
3. `su_changes` (DbCollection2 on `GameChange`) reads the grown-ups' changes from the backend. On fetched, on failure,
   or when the 4 s run out, `su_apply` lays them over the tables once (`settings/apply.js` `applyOnce`). **The game
   already opens without a backend.** That pattern is the one to copy.
4. `su_open` calls `Scripts.save.mend(stored.save)` and writes the result back to `gala.save`. It does this once,
   guarded by the Variable `ready`.
5. `su_setReady` sets `ready`. `/Pages/Game`'s `gm_root.mounted` waits on it.

### The backend that already exists

- `app/nodegx.project.json` → `metadata.cloudservices` points at a **NodeGX backend at `http://127.0.0.1:8585`**
  (`backend_mvi4i1s8eudt8`). That address is the maker's own computer, so **today no other device can reach it**.
- There is one collection, **`GameChange`**: grown-ups' edits to the game's tables, such as a step's name, a price, the
  starting stars, or a new costume or step.
- There are three cloud functions under `app/components/__cloud__/`:
  - `claimGrownup`: the first account to sign up gets the role `grownup`, and every later account is refused.
  - `saveChange` and `removeChange`: only for `role:grownup`. They re-check every change server-side (the checker is
    pasted into the function; see below).
- **`app/nodegx.security.json`**: everything is "nobody" by default. `GameChange` can be read publicly but written by
  nobody, so only the cloud functions write it, which shows that cloud functions run with server rights.
  `saveChange` and `removeChange` require `role:grownup`, `claimGrownup` requires `authenticated`, and
  `"signup": "public"`.
- **`/Pages/Grownups`** does username + password sign-in (`net.noodl.user.LogIn` / `SignUp` / `LogOut` /
  `User`). It calls `claimGrownup` after signing in or up, then shows the table editor only to the `grownup` role.
- **Model: one backend per home**, with "the home's grown-up". There is no notion of a family or of a child yet, and
  the game itself (`/Pages/Game`) never signs anyone in.
- Tooling: `tools/check.src.js` is the grown-ups' checker. `tools/sync-check.mjs` writes it into
  `app/scripts/settings/check.js` for the browser and into `tools/check.cloud.js`, which is pasted into
  `saveChange`, because "cloud functions cannot use script files yet". **`tools/cloud-save.glue.js` is not a cloud save
  of progress.** It is the tail of `saveChange`'s script.

## 2. The plan

### Decisions in one paragraph

The device stays the first place progress is kept: **local first**, as today. Each child's save is also kept on the
server as one document with a revision number. A child's device sends its save in the background after changes, and
the server accepts it only if it builds on the revision the server has. When two devices disagree, the copy with more
progress wins, and **the other copy is never thrown away**: it goes into a server-side history that the grown-up can
restore from. A grown-up creates the children. Children sign in with a **made-up "dancer name"** (no email, no real
name needed) and a **picture password** (4 pictures out of 12). A device remembers which children have played on it,
so on the family tablet a child just taps their face. Without signing in the game is exactly what it is today.

### 2.0 Before anything else: a backend other devices can reach

A child playing on the school laptop needs a server on the internet. Today the backend is `127.0.0.1:8585`.

- Put the app and its backend on a host with HTTPS (`npx nodegx-deploy` from `@nodegx/preview` writes the folder to
  upload), and point `cloudservices.endpoint` at it.
- The plan keeps the existing model of **one backend per home**: one grown-up, their children, their own table
  changes.
  - If the game is meant to be one shared server for many families, `claimGrownup` ("only the first account") has to
    become per-family: a `Family` record and a grown-up per family.
  - The data below already carries a `familyId` so that change stays small. **This is the decision I am least sure
    of; see part 4.**
- Generate one secret for signing device tokens (below), named `PROGRESS_TOKEN_KEY`. Using `set_function_secret`
  without a value, the grown-up pastes it into the project's `.env` file as `PROGRESS_TOKEN_KEY=…`. It never goes into
  a project file or the chat.

### 2.1 Data

**On the server** (new collections; permissions "nobody" for every operation, so only cloud functions touch them):

| Collection | Fields | Notes |
|---|---|---|
| `Player` | `userId` (unique), `familyId`, `displayName`, `avatar` (an icon id), `dancerName`, `tokenVersion` (number), `createdBy`, `createdAt`, `lastPlayedAt`, `devices` (array of `{deviceId, label, linkedAt, lastSeenAt}`) | One per child. `displayName` is what the grown-up typed. It is checked with the same `cleanName` + rude-word filter the grown-ups' checker already has. |
| `Progress` | `userId` (unique, used with `upsertOn`), `save` (JSON text), `rev` (integer), `updatedAt` (server time), `deviceId`, `lastOpId`, `summary` (`{season, stars, galaNights, schoolName}`) | One per child. The `summary` lets the grown-up's page and the "which school?" question show something without parsing saves. |
| `ProgressHistory` | `userId`, `save`, `rev`, `reason` (`conflict` / `adoptedGuest` / `beforeReset` / `beforeRestore` / `daily`), `at`, `deviceId`, `summary` | The safety net. Capped at about 30 rows per child, deleting the oldest, but `adoptedGuest` rows are never deleted. |

The child's **user account** is created with username = `dancerName` and password = the picture code. It has no email
and gets role `child`.

**On each device** there is one new persisted Global Store, **`players`** (`storageKey: "gala-players-v1"`):

```
{ deviceId,                       // random, made once
  current: null | userId,         // who is playing now; null = playing without signing in
  guest:   null | save,           // the "no one signed in" save, parked while a child plays
  slots: { [userId]: {
      displayName, avatar, dancerName,
      token,                      // device token for this child on this device (see 2.3)
      save,                       // this child's latest save on this device
      rev,                        // the server revision this save builds on
      dirty, pendingOpId,         // changed since the server last confirmed?
      lastSyncedAt, rememberHere  // false on a shared/school computer
  } } }
```

The existing **`gala` store keeps its role**: it holds *the save being played now*, so not one of the components that
subscribe to `gala.save` has to change.

- Switching player means three steps, in this order:
  1. copy `gala.save` into the outgoing slot (or into `guest`);
  2. write the incoming slot's save into `gala.save`;
  3. set `current`.
- Because of that order, a crash between steps leaves the save in two places, never in none.
- Someone who never signs in only ever has `gala-game-v2`, which is exactly today's storage.

### 2.2 Server-side workflows (cloud functions under `__cloud__/`)

All follow the pattern of the existing `saveChange`:
- `noodl.cloud.request`, then checks in a Function, then DB nodes, then `noodl.cloud.response` with a reason word on
  refusal;
- the reason words become `gm_*` messages, as `gp_said` already does.

| Function | Who may call | What it does |
|---|---|---|
| `addChild(displayName, avatar)` | `role:grownup` | Checks the name with `cleanName`. Generates a unique `dancerName` from the game's own word lists, e.g. `etoile-lapin-27`; it is checked against the rude-word list and unique among users. Generates a 4-picture code. `noodl.cloud.createuser` (username = dancerName, password = code, no email) → `addusertorole child` → creates `Player` and an empty `Progress` (`rev: 0`, no save). Returns `dancerName` and the picture code **once**, for the sign-in card. |
| `listChildren()` | `role:grownup` | Players with `summary`, `lastPlayedAt` and devices. |
| `newPictures(userId)` | `role:grownup` | New code (`noodl.cloud.updateuser` password, which also revokes that child's sessions) and `tokenVersion + 1`, so every device has to sign in again. For a forgotten code or a lost laptop. |
| `forgetDevice(userId, deviceId)` | `role:grownup` | Removes one device. Its token stops working because `saveProgress` checks the device list. |
| `removeChild(userId)` | `role:grownup` | Asked twice in the UI. Deletes the user, Player, Progress and history. |
| `listHistory(userId)` / `restoreProgress(userId, historyId)` | `role:grownup` | Restoring first saves the current save as `beforeRestore`, then writes the old one with `rev + 1`. |
| `linkDevice(deviceId, label)` | `role:child` (just signed in) | Adds the device to `Player.devices` and signs a **device token** (`noodl.cloud.jwtsign`, key from the `PROGRESS_TOKEN_KEY` secret, claims `{userId, deviceId, tv: tokenVersion}`, 180 days). Returns the token, the profile and the current `Progress` (`save`, `rev`, `summary`). |
| `loadProgress(token)` | public + token | `jwtverify` → checks `tv` and `deviceId` against `Player`. Returns `{save, rev, updatedAt}`. |
| `saveProgress(token, save, baseRev, opId, keepOther?)` | public + token | See below. |

**Why device tokens rather than the normal sign-in session.** A browser holds one sign-in session (one
`net.noodl.user.LogIn` at a time). Two children sharing a tablet would sign each other out, and a child whose changes
are still waiting to be sent could not send them while their sibling is signed in.

With a token per child per device:
- the picture password is checked once, on that device, by the real `LogIn`;
- the device then keeps each child's token and sends any child's waiting changes in the background, whoever is
  playing;
- right after `linkDevice` the app signs the child out of the browser session (`LogOut`), so the grown-ups' page is
  never left signed in as a child.

**`saveProgress` step by step:**

1. Verify the token, `tokenVersion` and device. Refuse with `signInAgain` otherwise.
2. Check the save with a **save checker**. It is generated like `check.cloud.js`, from a new `tools/progress.src.js`
   by a `tools/sync-progress.mjs`, so the browser and the server run the same code. It checks:
   - JSON under ~256 KB;
   - `v === 2`, `plan` and `school` objects, `season` an integer from 1 to 20, `stars` and `earned` integers from 0
     to 1,000,000, `notebook` an array of at most 50 entries, and the school name passes `cleanName`.
   - This is not meant to stop cheating: it is the child's own game. It stops broken or huge data getting in.
3. If `opId === Progress.lastOpId`, answer `ok` with the current `rev`. This makes a retry after a dropped answer
   harmless.
4. If `baseRev === Progress.rev`, write the save with `rev + 1`, `updatedAt` and `summary`, using
   `SetDbModelProperties` with **`onlyIfUnchanged: rev`**, so two simultaneous calls cannot both win.
   - Before writing, if the new save has *less* progress than the stored one, store the old one in history as
     `beforeReset`. Less progress means a lower season, fewer notebook entries, or a fresh school, as after
     "Start again" in the Notebook.
   - Also store a `daily` copy the first time the save is written each day.
5. Otherwise answer `conflict` with the server's `save`, `rev` and `summary`. Nothing is written.
6. If the client calls again with `keepOther` (the copy it decided to keep) and the server's `rev`, the server first
   puts the copy it is replacing into history (`conflict`), then writes.

`nodegx.security.json` gets:
- `Player`, `Progress` and `ProgressHistory` with every operation "nobody";
- the grown-up functions with `role:grownup` and `linkDevice` with `role:child`;
- `loadProgress` and `saveProgress` callable without a session (`allowNoAuth` on their request node), because the
  token is their check.

I would ask for a tight rate-limit class on `LogIn` and on these two functions (`get_backend_ops_config`). `"signup"`
stays `"public"` because `claimGrownup` needs it, but an account that signs up by itself gets neither role, so it can
do nothing.

### 2.3 How a child signs in

1. **The grown-up sets the child up** on `/Pages/Grownups`, in a new "Children" section shown only to `isGrownup`:
   - they type a first name or nickname and pick an avatar from the game's icons, then press **Add**;
   - the page shows a **sign-in card**: avatar, "Dancer name: etoile-lapin-27" and the 4 pictures in order. It can be
     printed;
   - the same section lists each child, with their season, stars and last played, plus "New pictures", the devices
     ("Forget this device"), "History" and "Remove".
2. **First time on a device.** On the game, the Top Bar gets a new chip: 👤 "Sign in" for a guest, or the child's
   avatar and name. It opens the **Who's playing?** overlay, `/Game/Who Is Playing`, styled like `Game/Season Letter`.
   - The overlay shows the faces of the children already linked to this device, **Play without signing in**, and
     **Someone new**.
   - "Someone new" asks for the dancer name (typed) and the 4 pictures (tapped from a 12-picture grid), then:
     `LogIn(dancerName, code)` → `linkDevice` → `LogOut`. The token, profile and server progress go into the child's
     slot.
   - A checkbox **"This is a shared computer (school)"** sets `rememberHere: false`. The slot then lives only for
     this visit: it is not written to `players`, it is removed when the child signs out or the tab closes, and every
     change is sent at once.
3. **Coming back on the same device.** The child taps their face and goes straight in; the token is already there. A
   face on a family tablet is not a lock, and I think that is right for siblings. If the family wants it, an option
   can ask for the pictures again on every switch.
4. **Switching child** runs the store swap in 2.1. The outgoing child's changes keep their `dirty` flag and are sent
   in the background with their own token.
5. **Signing out** ("Play without signing in") parks the child's save in their slot and brings back `guest`.

### 2.4 Progress already on a device (the first sign-in)

The device's existing progress is today's `gala-game-v2` save, which becomes `guest`. At a child's first sign-in on
this device, the app compares it with what the server has. "Has progress" means season > 1, or a notebook entry, or a
school name, or a purchase.

| Device guest save | Server save for this child | What happens |
|---|---|---|
| no progress | none | Start fresh. |
| no progress | some | Load the server save. The guest save stays as `guest`. |
| **has progress** | **none** (a new child) | **The device's school becomes the child's.** It is uploaded (`adoptedGuest` copy in history too) and the child is told "Your school is now saved in your name." The guest slot becomes a fresh school, so a sibling cannot take the same progress by accident. A local copy of the old guest save is kept for 30 days, so the grown-up can undo it. |
| **has progress** | **some** | **Ask, never guess.** Show both schools side by side (name, season, stars, gala nights) and "Which school is yours?" The one picked becomes the child's. The other is **not deleted**: if it was the device's, it stays as the guest school; if it was the server's, it goes to history (`conflict`). |

### 2.5 Sync and what happens offline

- **Sending.** A new logic component, **`/Logic/Progress Sync`**, sits in `/App` next to `Start Up`, so it keeps
  running on both pages.
  - It subscribes to `gala.save` and `players`.
  - When the save changes and `current` is a child, it copies the save into the slot and sets `dirty`.
  - It sends after about 3 s without changes, and at once after `runDone` of a gala night, `nextSeason`, a reset and a
    player switch.
  - It also sends on `visibilitychange` → hidden and on `pagehide`. These need a small Function with window
    listeners, the way `/Game/Stage 3D` already listens to `resize`.
  - The logic lives in a new pure script, `scripts/game/sync.js`, with no NodeGX in it so it can be tested: what to
    send, the answer to a reply, backoff, conflict choice. The component just wires it to `CloudFunction2` nodes,
    much as `/Game/Dispatcher` wires `dispatch.js`.
- **The sending queue.** One save per child, not a list of changes. A save is the whole state, so the latest one is
  the only one worth sending. `pendingOpId` is kept until the server says `ok`.
- **When the connection drops.** Nothing changes for the child.
  - Every press is already in localStorage before any network is involved.
  - Failed sends retry with backoff (5 s → 10 s → … → 5 min), and right away on the browser's `online` event or the
    next change.
  - The Top Bar sign shows ☁︎✓ "saved", ☁︎… "waiting to send" or ☁︎✕ "not sent yet, it is safe on this device".
    That sign gives the reassurance without blocking play.
- **A gala night the connection drops in the middle of** plays entirely on the device. The stars and notebook entry
  are written locally at `runDone`, then sent. If the tab itself closes mid-evening, the evening was not finished,
  exactly as today, and replaying gives the same evening (same seed).
- **Starting up offline.** `Start Up` opens `current`'s slot from `players` with no network at all. It reads the
  server copy in the background (`loadProgress`, with the same "don't wait more than 4 s" idea as `su_wait`) and only
  then decides whether there is something newer.
- **Conflicts** (the child played on the laptop, then on the tablet that had old changes waiting): the server answers
  `conflict` and `sync.js` decides:
  - if the device copy has more progress (season, then gala nights, then stars `earned`), it calls `saveProgress`
    again with `keepOther`, and the server's copy goes to history;
  - otherwise the server's copy replaces the device's, and the device's copy is sent to history;
  - the child sees one plain sentence: "Your school from another device was further along, so we kept that one. The
    other one is safe with your grown-up."
  - Either way both copies exist afterwards.

### 2.7 What could go wrong

- **Hosting model.** If the game should serve many families from one server, "first account is the grown-up" is wrong
  and needs a `Family` record first. Decide before step 3.
- **The `gala-game-v2` key.**
  - Changing its name, shape or `persist` would lose today's players' progress, so it stays exactly as is.
  - Separately, `mend()` silently starts fresh on anything it cannot read. Every save from the server must go through
    the save checker **before** `mend`. A refused save is kept aside (history) rather than turned into a fresh school
    that would then be sent and overwrite the real one.
- **A fresh save overwriting a real one.** This is the most likely way to lose progress, for example a new device
  sending its empty starting school before it has read the server.
  - The rule: a slot never sends until it has completed one `loadProgress` or `linkDevice` (it knows a `rev`).
  - The server rule: a save with less progress is always copied to history before it is replaced.
- **Two children, one browser session.** Signing into the grown-ups' page while a child plays, or a child opening it,
  shares the one `LogIn` session. The device tokens and the `LogOut` right after `linkDevice` keep these apart, but the
  grown-ups' page needs testing with children on the device.
- **Shared and school computers.** A remembered slot on a school laptop lets the next child play as this one. Hence the
  "shared computer" box, "Forget this device" for the grown-up, and `newPictures` revoking every token.
- **Picture passwords are weak** (12⁴ = 20,736 codes). They are acceptable for an 8–13 game holding nothing sensitive
  (only a dance school's state, a first name and an avatar), and only with rate limiting on `LogIn`, and only because
  the dancer name also has to be known.
  - The backend's minimum password length is unknown. The code is sent as a longer string such as
    `tutu.cygne.etoile.lune`.
- **Children's data.** Store only a first name or nickname chosen by the grown-up, an avatar and the game save. No
  email, no age, no real name required. "Remove" deletes everything.
- **localStorage size.** Each save is tens of KB, so a few children per device are fine. Writing `players` on every
  press costs a little and needs measuring; if it is too slow, the slot copy can be written only when sending.
- **Generated code.** The server-side checker is pasted into a cloud function, like `check.cloud.js`. Someone has to
  re-run the generator when the save's shape changes, and `tools/check-progress.mjs` should fail if the pasted copy is
  out of date.
- **The grown-ups' table changes apply to every child.** A grown-up lowering a price changes it for all their children.
  That is how `GameChange` works today, and I would leave it.

## 3. What I would check to know it works

**Scripts (Node, no browser)**, in `tools/check-progress.mjs`, next to `check-views.mjs` and `check-rules.mjs` (all
three pass today):
- `compareProgress` puts saves from the existing played-through fixture (the one `check-views.mjs` builds) in the
  right order.
- Every row of the first-sign-in table in 2.4 gives the stated result.
- `sync.js` cases:
  - ok;
  - network error → retry with backoff;
  - a dropped answer, then a retry with the same `opId` → no duplicate and no conflict;
  - conflict where the device has more progress / less progress;
  - `signInAgain`;
  - a slot that never loaded must never send.
- The save checker accepts `fresh()`, `nextSeason()` saves and a full played save. It refuses one that is too big,
  has `v: 1`, has a rude school name or has a negative number of stars. The browser copy and the cloud copy are
  identical.
- `node tools/check-rules.mjs`, `node tools/check-views.mjs` and `gala-rules` `npm test` still pass. The feature
  must not touch the rules.

**Backend**, with `check_backend_access` and direct calls:
- Anonymous, self-signed-up, child and grown-up callers against every collection and function. Children cannot read
  another child's progress or call grown-up functions; nobody can read `Progress` directly.
- `saveProgress` with:
  - a wrong token;
  - an old `tokenVersion` (after `newPictures`);
  - a forgotten device;
  - a stale `baseRev`;
  - two calls at the same moment (only one wins, and the other gets `conflict`).
- `claimGrownup` still refuses a child account.

**In the app**, with `drive_page` from the start page (no `page`), as a person arrives:
1. **Guest, unchanged.** Clear storage, play a few presses, reload. Same as today, no sign-in asked, and
   `localStorage["gala-game-v2"]` has the same shape as before.
2. **Existing player keeps progress.** `seed_storage` a played `gala-game-v2` (season 2, a notebook entry), sign in
   as a new child → the same school, now in the child's name; the server `Progress` has it; the guest school is fresh.
3. **Ask when both exist.** The same seeded device plus a child who has server progress → the "which school?" question.
   Each answer leaves the other copy as guest or in history.
4. **Another device.** Sign in as the child on a clean browser → their school exactly, with the same season, stars,
   costumes and formations.
5. **Two children, one device.** A plays, switch to B, B plays, switch back → each has their own. B's changes are sent
   while A plays.
6. **Connection drops.** `stub_route` the backend to fail, then play, including a whole gala night → the Top Bar says
   "not sent yet"; reload still offline → nothing lost; remove the stub → sent; the server has it.
7. **Conflict.** Play offline on device 1, play further on device 2, bring device 1 back → the further school wins and
   the other is in the grown-up's history; restore it from there.
8. **Shared computer.** Box ticked, close the tab, reopen → no face is offered and no save is left in `players`.
9. **Grown-up.** Add a child (a rude name is refused), print the card, new pictures (the old device must sign in
   again), forget a device, remove a child.
10. Everything above in English and in French, and on a narrow screen (the sheet becomes a bottom sheet).

## 4. How I found my way around

**Easy:**
- The graph print (`--graph`) is readable. Every component and many nodes carry a sentence saying what they are for,
  and the comments explain *why*: for example why `su_wait` exists, why `dp_fn` runs only on a press, and why the
  checker is pasted into the cloud function.
- The architecture is very regular, which made the feature's seams easy to find. It is one event bus (`gala-act`), one
  dispatcher, pure action functions, and one `gala.save` store that everything subscribes to.
- `game/save.js` and `game/actions.js` are short and pure.
- The tools in `tools/` say at the top what they generate from what. Running `check-rules`, `check-views` and the
  `gala-rules` tests gave me a green baseline in seconds.

**Hard, or misleading:**
- **`tools/cloud-save.glue.js` sounds like a cloud save of progress. It is not.** It is the tail of the grown-ups'
  `saveChange` script. There is no server-side progress at all today.
- `rules/*` and `stage/*` look editable but are generated. `stage/*` is generated from `reference/src`, which is
  missing, so `tools/sync-stage.mjs` and `tools/extract-words.mjs` cannot be re-run. The plan doesn't need them.
- The graph print is about 240 KB. I read the cloud functions, `App`, `Start Up`, `Dispatcher`, `Pages/Game`,
  `Pages/Grownups`, `Top Bar`, `Sheet`, `Notebook`, `Stage 3D`, `Toast` and `Season Letter` closely. I skimmed or
  skipped the tabs' insides (Formation, Costumes, etc.), which only read and change the save through the dispatcher.
- I worked out what the backend can do (`createuser`, `updateuser`, `jwtsign` / `jwtverify`, `onlyIfUnchanged`,
  `upsertOn`, `allowNoAuth`) from the node catalog inside `node_modules/@nodegx/mcp`, not from running it.

**Where I am unsure:**
- **One backend per home or one for everyone?** The existing words ("the home's grown-up") and `claimGrownup` say one
  per home, so the plan assumes that. "A laptop at school" works either way once the backend is online, but if this is
  meant to be a public service, steps 2–3 change (a `Family` record and per-family grown-ups).
- **Whether cloud functions really bypass the collection permissions.** I inferred it from `saveChange` creating
  `GameChange` rows that "nobody" may create. I did not test it.
- **Whether `jwtsign` reads its key from a secret the way the plan needs**, the rate-limit settings, and the backend's
  password rules. I have not seen these in use; each is checked in step 2 or 3 before relying on it.
- **Whether a Global Store's `storageKey` can change at run time.** I assumed not, which is why the plan uses one
  `players` store holding every slot rather than one store per child.
- **What the `LogIn` session does offline**, and how long it lasts. The device-token design is meant not to depend on
  it, but I have not seen it.
- **I did not run the app** (`npx @nodegx/preview`) or open the project with the `nodegx` server. Everything here
  comes from reading the graph and the scripts and running the three existing checks.
- **Picture password vs. PIN, and "tap your face, no password" on a family device.** These are product choices I made
  without asking. They are easy to change, and the server design doesn't depend on them.
