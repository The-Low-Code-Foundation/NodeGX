# Plan: children sign in online and keep their progress

Status: plan only. Nothing in the app has been changed.

---

## 1. How the game works today

### What it is

**Le Gala de danse** is a management game in French and English. The player runs a dance school and gets
ready for its end-of-year show (the *gala*). On the preparation tabs they set the running order (Programme),
place the dancers and build the choreography (Formation), choose the snacks (Goûter), dress each number
(Costumes), furnish the dressing room (La loge), and from season 2 run the car park (Parking). Stars buy things
in the Shop. The evening itself plays out in a 3D view of the school (three.js). It can be a dress rehearsal
(no stars, no record), a try-out of one number, or the real gala night. The gala night earns stars, writes an
entry in the school's Notebook (Carnet), and unlocks "Next season", where new classes join. The Notebook also
has "Start again".

There's a second page, **Réglages des grands** (grown-ups' settings). A signed-in grown-up can change the game's
tables there (step difficulty, prices, names, a new school's starting stars) and add costumes and steps.

### How it's built

- `app/` is a **NodeGX project** (`nodegx.project.json`, format 5, runtime react19) with 54 components, 762
  nodes and 874 wires. I read it as text with `npx -y @nodegx/mcp@0.2.4 app --graph`.
- Most of the logic is plain JavaScript in `app/scripts/`. Graph Functions reach it through `Scripts.<name>`, and
  the files load each other with `use('folder/file')`:
  - `scripts/rules/*` is the game's rules engine (`simulate`, the data tables, tunes). These files are
    **generated** from `gala-rules/src` by `tools/sync-rules.mjs`, and `tools/check-rules.mjs` checks the copy
    still plays the same evening. `gala-rules/` has its own tests (`npm test`, 19 tests, all pass today).
  - `scripts/game/dispatch.js` turns one button press (`act`, `arg`) into `{ save, ui, toast }`.
  - `scripts/game/actions.js` has the pure functions behind each press (`buy`, `formationAct`, `costume`,
    `build`, `finishGala`…).
  - `scripts/game/save.js` defines the **save's shape**: `fresh(lang)`, `mend(input)` (repairs an old save or
    starts a fresh one), `nextSeason(save)`, and `fromRound1` for an even older format.
  - `scripts/view/*` turn the save and screen state into what each tab shows.
  - `scripts/stage/*` is the 3D school and the music. It's generated by `tools/sync-stage.mjs` from
    `reference/src`, **which isn't in this folder**.
  - `scripts/settings/check.js` (generated from `tools/check.src.js` by `tools/sync-check.mjs`) checks a
    grown-up's change. It includes `cleanName()` and `rude()`, a filter for unkind words in French and English.
    A copy of it is pasted into the cloud function `saveChange`, because cloud functions can't load script
    files.
- **Events, not wires, carry presses.** Every button sends the event `gala-act` with `act` and `arg`.

### The parts this feature touches

**Where the progress lives today: on this device only.**

- `/Logic/Start Up`, node `su_gala`: a **persisted Global Store** named `gala` (`persist: true`,
  `storageKey: "gala-game-v2"`), i.e. the browser's localStorage. The whole game's progress is one object
  under the key `save`.
- The save (about 3 KB fresh and about 4 KB by season 5) looks like this:
  `{ v: 2, lang, season, galaDone, seenIntro, plan: {order, start, interval, numbers{…formation, blocks, costume},
  hair, cakeG, bottles, backdrop…}, school: {name, logeCols, stars, earned, owned, upgrades, furniture},
  notebook: [{season, at, points, satisfaction, nums}], sound, seed }`.
- The second store, `ui` (not persisted), holds only what's on screen: the tab, selections, the live evening
  (`res`, `live`), the camera and the toast.

**Exactly two places write the save:**

1. `/Logic/Start Up`: `su_open` ("Open the save") runs once, after the grown-ups' changes are laid over the
   tables (`su_apply`) and the store has loaded. It calls `Scripts.save.mend(stored.save)` and writes the
   result with `su_setSave`, then sets the Variable `ready`. `/Pages/Game` only mounts the game when `ready` is
   set.
2. `/Game/Dispatcher` (placed in `/Pages/Game`): `dp_fn` hears `gala-act`, calls
   `Scripts.dispatch.dispatch(...)`, and writes a new save through `dp_setSave`. Everything that changes progress
   goes through here: purchases, formation edits, `runDone` (which calls `finishGala` and adds stars and a
   notebook entry), `nextSeason`, `note:resetYes` ("Start again" → `fresh()`), `lang` and `sound`.

**Everything else only reads the save** with `net.noodl.GlobalStore.Subscribe {storeName:"gala", keys:"save"}`:
Top Bar, Camera Bar, Sheet, Live, Results, Season Letter, every tab, Stage 3D (`s3_sync` calls
`stage.sync(save, ui)` on every change) and the Grownups page (for the language). So if the current save is
swapped in that one store key, the whole game follows. That fact shapes the plan.

**A game run is local.** `begin()` in `dispatch.js` asks the 3D stage for `beginRun(mode)`, which simulates the
whole evening up front (`res`) and then animates it. When it ends, the stage sends `runDone`, and only then is
the save changed (`finishGala`). No network is involved. Closing the tab in the middle of a gala loses that
evening today, with or without a connection, and that's existing behaviour.

**There's already a backend, and already accounts, but only for one grown-up:**

- `nodegx.project.json` → `metadata.cloudservices` points at a NodeGX backend at
  `http://127.0.0.1:8585` (`backend_mvi4i1s8eudt8`). It's **local to this computer**, so nothing is online yet.
- `nodegx.security.json`: everything defaults to `nobody`. The collection `GameChange` is publicly readable and
  can't be written directly. The cloud functions `saveChange` and `removeChange` need `role:grownup`, and
  `claimGrownup` needs `authenticated`. `"signup": "public"`, so anyone can make an account.
- `/__cloud__/claimGrownup` makes **the first account that ever signs in on the Grownups page** the `grownup`
  and refuses everyone after that. The `grownup` role is **global to the backend**. It means "the person who
  runs this game's settings", not "a parent in a family".
- `/__cloud__/saveChange` and `/__cloud__/removeChange` write `GameChange` rows. `/Logic/Start Up` reads them
  all (`su_changes`, waiting at most 4 s with `su_wait` so the game still opens offline) and lays them over the
  tables for **everyone**.
- `/Pages/Grownups` has a username + password form (`gp_user`, `gp_pass`, `net.noodl.user.LogIn`,
  `SignUp` and `LogOut`, and `net.noodl.user.User` for who is signed in), and calls `claimGrownup` after every
  log-in or sign-up.
- The top bar's ⚙︎ chip (`tb_grown`) navigates to `/Pages/Grownups`.

The pattern the author set up, which I'll follow: **all writes go through cloud functions that check
everything again, and direct collection access is `nobody`**. Checks that run in both the browser and the
cloud come from one source file plus a `tools/sync-*.mjs` generator.

## 2. The plan

### 2.1 Decisions first

| Question | Decision |
|---|---|
| One backend for all families, or one per home? | **One shared, hosted backend** (it has to be online for "another device" to work). Families are rows in it. |
| Who's a "grown-up"? | Keep the existing global `grownup` role as **the game's operator** (game settings). Add a new role **`parent`** for a family's grown-up. They aren't the same person. |
| How does a child sign in without email? | A **player card** made by the parent: a *player code* (e.g. `luna-4827`) plus a **picture secret** (3 pictures in order from a grid of 36). No email, no date of birth, and a nickname instead of a real name. |
| Where's the truth? | **Local-first.** The device's copy is what the child plays. The server copy is what follows them to another device. They're reconciled with a version number and, when both changed, a **three-way merge**. |
| What's stored about a child? | Nickname, avatar picture, player code, family, and the save. Nothing else. |

### 2.2 Data

**On the backend** (all collections `nobody` in `nodegx.security.json`, read and written only through cloud
functions, as `GameChange` writes are today):

| Collection | Fields | Notes |
|---|---|---|
| `Family` | `name`, `code` (6 letters, unambiguous alphabet), `parent` (user id), `createdAt` | One per parent account. |
| `Child` | `user` (the child's user id), `family`, `nickname`, `avatar`, `playerCode` (unique) | **Membership lives here, not in user properties**: a signed-in user can normally edit their own user record, so a `family` property on it couldn't be trusted. |
| `Progress` | `child`, `save` (JSON string), `saveV` (the save format, 2 today), `version` (integer, +1 per accepted write), `lastOpId`, `lastDevice`, `updatedAt` | Exactly one per child. |
| `ProgressBackup` | `child`, `save`, `version`, `reason` (`conflict`, `reset`, `adopt`, `season`, `restore`), `createdAt` | The safety net. The last 20 per child are kept, pruned by `pushProgress` itself. |

Child **user accounts** (the built-in user class): `username = playerCode`, `password = the picture secret`
(the ids of the 3 pictures joined), and role `child`. They're created only by the cloud function `addChild`,
never by public sign-up.

**On the device**: the existing persisted store `gala` (`storageKey "gala-game-v2"`) gets **new keys next to
`save`**. The key name and the persistence stay exactly as they are, so nothing on any device has to move on
upgrade:

```
gala.save      the save being played right now (unchanged meaning: every Subscribe keeps working)
gala.active    null = the guest is playing; otherwise a child id
gala.guest     the guest's save, parked here while a child plays (absent until a child first signs in here)
gala.players   { [childId]: { nickname, avatar, playerCode, save, base, baseVersion, rev, sentRev, lastSyncedAt } }
               base = the save as the server last confirmed it (needed for the three-way merge)
gala.family    { code, name } once a parent has set this device up for their family (for the avatar picker)
gala.device    a random device id
```

After the upgrade, an existing device has `active` absent, which means the guest is playing. The guest's save is
the `save` it already has, untouched.

### 2.3 Server-side workflows (cloud functions in `/__cloud__/`)

Each one starts like the existing ones: `noodl.cloud.request` → who's calling (`userId`, `getuserroles`) → read
→ a `JavaScriptFunction` that decides → write → `noodl.cloud.response`, with a reason code on failure.

| Function | Who may call (security.json) | What it does |
|---|---|---|
| `createFamily` | `authenticated` | The caller has no family and isn't a child. It creates a `Family` with a unique code and adds the caller to `parent`. |
| `addChild` | `role:parent` | Checks the nickname (`cleanName` + `rude`, same checker as today), chooses an avatar and makes a unique `playerCode`. The server picks a random picture secret, then runs **Create User** (username, password, no email), Add User To Role `child`, then creates `Child` and an empty `Progress` (version 0). It returns the code and secret **once** so the parent can show or print the card. It caps the number of children per family (say 8). |
| `listChildren` | `role:parent` | The caller's family's children (nickname, avatar, code, last played, season and stars from `Progress`). Used by the parent page and to set up a device. |
| `resetChildSecret` | `role:parent` | Only for a child of the caller's family. It sets a new random picture secret (Update User, password) and returns it once. |
| `removeChild` | `role:parent` | Only for a child of the caller's family. It deletes `Progress`, `ProgressBackup`, `Child` and the user. Parents can delete their child's data. |
| `loadProgress` | `role:child` | Returns the caller's own `{ save, version, saveV, updatedAt }`. |
| `pushProgress` | `role:child` | Input `{ save, baseVersion, opId, device, appSaveV, reason }`. See below. |
| `listBackups` / `restoreBackup` | `role:parent` (and `role:child` for listing their own) | Lets a parent put an earlier save back. It's a new version, not a rewrite of history. |
| `claimGrownup` (existing, **changed**) | unchanged | It must also **refuse callers with role `child` or `parent`**. Today, on a brand-new backend, the first account to sign in on the Grownups page becomes the game's operator, and with children's accounts around, that could be a child. |

**`pushProgress`, step by step** (where the work is done):

1. Refuse if the caller has no `Child` row. Refuse a save over 64 KB, or one that isn't an object with
   `v`, `plan`, `school` and `notebook`.
2. **Version-skew guard:** if `appSaveV` is *lower* than the stored `saveV`, refuse with `updateTheGame`. An old
   copy of the app would otherwise `mend()` a newer save into a fresh one (see 2.8) and push that back.
3. **Idempotent:** if `opId === lastOpId`, answer "already saved" with the current version. That way a retry after
   a dropped answer does nothing twice.
4. If `baseVersion === version`, write with **Update Record, `onlyIfUnchanged: version`** (so two pushes that
   arrive together can't both win), set `version + 1`, and answer `{ ok, version }`. Before writing, if the new
   save goes *backwards* (lower season, a notebook that's shorter or empty, i.e. "Start again"), first copy the
   old save into `ProgressBackup` with reason `reset`. If the season went up, also make a `season` backup. These
   are the only scheduled-like workflows: I found no scheduled-job node, so pruning and backups happen inside
   this function.
5. If `baseVersion < version` (another device saved in between), **don't write**. Answer
   `{ conflict, version, save }`. The device merges (2.6) and pushes again with the new `baseVersion`.

The names the children type and the school name in the save are cleaned with the same `cleanName` that
`saveChange` uses. I'd extend `tools/check.src.js` and `tools/sync-check.mjs` to emit a second pasted body,
`tools/check.progress.cloud.js`, because cloud functions still can't `use()` script files.

### 2.4 How a child signs in

**The parent, once** (new page `/Pages/Family`, reached from a "Family" chip next to ⚙︎ in `/Game/Top Bar`):

1. The parent signs up or signs in with username + password, plus an **email address recommended** so they can
   recover the account. The page reuses the form pattern from `/Pages/Grownups` (LogIn/SignUp/LogOut, User),
   then calls `createFamily`.
2. "Add a child": nickname + avatar → `addChild` → the **player card** on screen, printable: avatar, player code,
   and the 3 pictures in order. The parent sees each child's season and stars and can reset the picture secret or
   remove the child.
3. "Use this device for my family": stores `gala.family` and the children's nickname, avatar and code in
   `gala.players` (never the secrets). The family tablet then shows the children's avatars.

**The child:**

- **On the family tablet:** tap the player chip in the top bar (it shows "Guest" or your avatar), tap your avatar,
  then tap your 3 pictures. That's a Log In with `username = playerCode`.
- **On a school laptop:** "Sign in with my card": type the player code, then tap the 3 pictures.
- Signing out (or switching child) goes back to the guest's game on that device. The child's copy **stays on the
  device**, so they can carry on offline next time (see 2.7).
- Only one child is signed in to the backend at a time on a device (the browser holds one session). Switching
  child means signing in as them.

Two children on one device each get their own `gala.players[id]` slot, and the guest has `gala.guest`. Their
saves never touch each other.

### 2.5 What happens to the progress already on a device

- **After the update, before anyone signs in:** nothing changes. `gala.save` is the guest's game, as now.
- **A child's first sign-in on a device that has guest progress** (`hasProgress(save)`: season > 1, a notebook
  entry, stars earned, or anything bought or placed):
  - If the child's server progress is **empty** (version 0): ask "Bring this school with you?" and show the
    school card (name, season, stars). Yes → it becomes the child's save and is pushed with reason `adopt`. No →
    they start fresh. **Either way the guest save stays in `gala.guest`** on the device. Nothing is deleted, so a
    sibling who also played as guest can claim it too.
  - If the child **already has server progress**: show both schools side by side ("the one on this tablet" /
    "your school") and ask which one to keep playing. The one not chosen is saved as a `ProgressBackup` (reason
    `adopt`) and stays in `gala.guest`. A parent can restore it.
- **A device with no guest progress:** load the child's server save. No question.
- **Clearing the browser:** the guest's progress is lost, as today. A child who signs in again gets everything
  back from the server (minus whatever hadn't been sent yet, which the status chip warns about).

### 2.6 Keeping two copies in step (the merge)

Each child slot keeps `base` (the last save the server confirmed) as well as the save being played. When a push
gets `conflict`, the new pure function `mergeSaves(base, mine, theirs)` in `scripts/game/merge.js` decides, part
by part:

- `notebook`: the union of both, by `(season, at, points)`. A gala played on either device is kept.
- `school.stars`: `theirs + (mine − base)`, never below 0. `earned`: the same rule. Stars spent and earned on both
  devices both count.
- `school.owned` and `upgrades`: the union. For a count (`sieges`), the larger value.
- `season`, `galaDone`, `seenIntro`: whichever copy is further along. If one device moved to a new season, its
  `plan.numbers` for the new classes come along (`addSeasonNumbers`).
- `plan.*` (order, each number's formation and blocks and costume, hair, snacks), `school.furniture`, `name`:
  per part, **the copy that changed it since `base`** wins. If both changed the same part, `mine` wins (the child
  is looking at it). `theirs` is kept as a `ProgressBackup` with reason `conflict`.
- `lang` and `sound`: `mine`.
- The result goes through `Scripts.save.mend()` and is pushed with `baseVersion = theirs.version`.

This only happens when the same child played on two devices and at least one was offline, so it's rare. It
never throws anything away, because the loser always goes to a backup.

**When the device pulls.** At sign-in, when the game opens with a child active, and when the connection comes
back, the device calls `loadProgress`. If the server is newer and the local copy hasn't changed since `base`,
take the server's copy. If both changed, merge. Either way the new save is only put on screen while
`ui.screen === 'prep'`, **never in the middle of a run**. Otherwise it waits until the run ends.

### 2.7 Offline, and the connection dropping in the middle of a game

- **Every press is already saved on the device the moment it happens** (`dp_setSave` → the persisted `gala`
  store). Sync never sits between the child and their save. A rehearsal or gala night never needs the network
  (2.1).
- A new **`/Logic/Sync`** component (logic, placed in `/Pages/Game`) subscribes to `gala.save`. When a child is
  active and the save differs from their slot, it copies the save into `gala.players[active].save` and bumps
  `rev`. Then, after a 2-second quiet spell **and not during a run**, it calls `pushProgress`. The end of a run
  (`runDone`) pushes at once, because that's when stars and the notebook change.
- **No connection, a timeout, or a 5xx error:** keep `rev > sentRev` (meaning "not sent yet") and retry with a
  `Timer` backoff (5 s, 15 s, 60 s, then every 2 min), plus immediately on the browser's `online` event and when
  the tab becomes visible. The `opId` is made once per attempt *content* (child + rev), so a retry is the same op
  and step 3 of `pushProgress` makes it harmless.
- **The session expired** (the sign-in is too old): don't interrupt the game. The status chip says "Sign in to
  save online", and the save keeps building up on the device.
- **Offline sign-in:** a child who has signed in on this device before can tap their avatar and **play their
  local copy** while offline. It's marked "not sent yet" and pushed the next time they sign in online. (An
  offline sign-in can't check the picture secret. On a family device, I think that's acceptable: it only opens
  that child's copy on that device. A parent setting can turn it off.)
- **The status chip** (in `/Game/Top Bar`, next to the stars): your avatar plus ☁️✓ "saved online" / ⏳ "will
  save when online" / ⚠️ "sign in to save online". Only "saved online" means another device will see it.

### 2.9 What could go wrong

- **An old app version wipes a newer save.** `mend()` returns `fresh()` for any save whose `v !== 2`. If the
  save format ever moves to `v: 3`, an un-updated tablet would open a child's save as a brand-new school and push
  it. Guards: the client never pushes a save that `mend()` had to replace with `fresh()` over a non-empty base,
  the server refuses a lower `appSaveV`, and `pushProgress` backs up any backwards push.
- **"Start again" on one device** resets the child's online school everywhere. That's intended, but a `reset`
  backup is written first, and the confirmation should say so.
- **A child becomes the game's operator.** On a fresh backend, `claimGrownup` grants `grownup` to the first
  account. The fix is in step 3.
- **Settings are global.** The operator's `GameChange` changes apply to every family. That's fine for one
  operator, but it's not a per-family setting. Making it per-family is out of scope, and I'm flagging it.
- **Guessing a picture secret.** 36³ ≈ 47,000 combinations. That's fine against a sibling, and only fine against
  a stranger with login rate limiting (the built-in Log In can't count failures per account for a lockout).
  If the limit turns out too loose, sign-in should move into a cloud function that counts failures. I'm not sure
  that's possible with the nodes I found (see section 4).
- **Children's data and the law** (GDPR-K, COPPA and similar): a parent creates the accounts, no email or real name
  is collected for a child, and a parent can delete everything. A privacy note and the parent's consent belong on
  `/Pages/Family`.
- **Two children, one device:** a slot mix-up would put one child's school in another's account. `switchTo` is
  pure and tested, `Sync` only pushes the slot of the **signed-in** user id, and `pushProgress` checks the caller
  owns the `Progress`.
- **Space in localStorage:** about 4 KB per save, times (guest + children + bases), is small. Still, a write
  failure should show the ⚠️ chip rather than fail silently.
- **A save swapped in during a run** would confuse the 3D stage. Saves are only swapped in `prep`.
- **The tab closing mid-gala** loses that evening, as today. It could be fixed separately by marking the run
  in the save, but that isn't needed for this feature.

## 3. What I'd check to know it works

**Baseline before any change** (all pass today): `cd gala-rules && npm test` (19 tests),
`node tools/check-rules.mjs`, `node tools/check-views.mjs`. They must still pass after every step.

**Pure checks (`tools/check-sync.mjs`):**
- `switchTo`: guest → child A → child B → guest returns each save byte for byte. The guest save is never
  modified.
- `hasProgress`: false for `fresh()`, true after a purchase, a placed piece of furniture, or a gala.
- `mergeSaves`: stars spent on one side and earned on the other add up. Notebook entries from both sides
  survive. Owned items are the union. Both moving to season 2 doesn't make season 3. An identical save on both
  sides merges to itself. The result passes `mend()` unchanged.
- Version skew: a `v: 3` save is never pushed back as a fresh one.

**Backend, with `check_backend_access` and direct calls:**
- A child can't call `addChild`, `listChildren` or `removeChild`, and can't read or write another child's
  `Progress` (directly or through `pushProgress`). A parent can't touch another family's children.
- Public sign-up can't produce a `child` or `parent` role. `claimGrownup` refuses children and parents.
- `pushProgress`: the same `opId` twice → one version bump. Two pushes with the same `baseVersion` at once → one
  wins and the other gets `conflict`. A backwards push → a backup exists. An oversized or malformed save →
  refused with a reason.
- `removeChild` leaves no `Progress`, `ProgressBackup`, `Child` or user behind.

**End to end, with `drive_page` from the start page and two browser profiles standing in for two devices:**
1. A device with an existing pre-update save in `gala-game-v2` opens exactly where it was, and no sign-in is
   asked for.
2. A parent creates a family and two children and gets two printable cards.
3. Child A signs in on device 1, which has guest progress → "Bring this school?" → yes. On device 2, child A
   signs in → the same school (season, stars, formation, notebook).
4. Child B signs in on device 1 → their own school. Back to A → A's school. Sign out → the guest's school, untouched.
5. Go offline (stop the backend or block the network) in the middle of a gala night. It plays to the end, the
   stars and the notebook entry appear, and the chip shows ⏳. Reload the tab while still offline → still there.
   Back online → ✓, and device 2 sees it.
6. Child A plays offline on device 1 and online on device 2. Device 1 reconnects → merged: both galas are in the
   notebook, the stars add up, and there's a `conflict` backup.
7. Clear device 1's storage → child A signs in → everything back.
8. "Start again" signed in → the online save is reset and a `reset` backup is listed for the parent, who can
   restore it.
9. A rude nickname or school name is refused, with a kind message, in both languages.

## 4. How I found my way around

**What was easy:**
- `npx -y @nodegx/mcp@0.2.4 app --graph` gave the whole app on one page. Every component has a one-line
  description written for a person, and most nodes have a label and a comment saying *why* ("Run from the
  list's done or unchanged… so it cannot decide before the list has been read"). That's unusually good.
- The architecture is disciplined: one event channel (`gala-act`), one dispatcher, two writers of the save,
  pure action functions, and generated files that say where they come from and how to regenerate them. Finding
  "where does progress live and who writes it" took a few greps over the graph.
- The existing grown-up feature already shows the house style for a backend: cloud functions that check
  everything, collections closed by default, and one checker shared by browser and cloud.

**What was hard or surprising:**
- `reference/src` (the original hand-coded game) is referenced by `tools/sync-stage.mjs`,
  `tools/extract-words.mjs` and many comments, but **it isn't in the folder**. The 3D stage scripts and the words
  can't be regenerated, so new words have to be added by hand in two places.
- `tools/cloud-save.glue.js` sounds like an existing cloud save of progress. **It isn't**: it's the tail of
  the grown-ups' `saveChange` function. There's no cloud save of game progress today.
- The `grownup` role reads like "a parent", but it's one account per backend: the game's operator. The plan
  depends on keeping those apart.
- The Grownups page's description says "(being built)", so that part of the app may still change under this
  plan.

**Where I'm unsure** (I didn't open the project with the NodeGX server, so as not to write anything. I couldn't
look at the local backend's config, and I read node capabilities from the server's node catalog rather than by
trying them):
- That a persisted Global Store keeps **extra keys** (`active`, `guest`, `players`…) next to `save` across
  reloads, the way it keeps `save`. If it only persists some keys, the device data would need its own persisted
  store (`gala-device-v1`) and a one-time read of the old one.
- That **Create User** in a cloud function accepts a username and password with no email, that **Update Record
  with Only If Unchanged** behaves as a compare-and-set inside a cloud function, and that a signed-in user can
  edit their own user properties (I assumed they can, which is why membership is in `Child`).
- Whether the backend can **rate-limit or lock out** log-in attempts per account, which decides whether picture
  secrets are strong enough or sign-in should go through a cloud function.
- That there's **no scheduled-job node**. I didn't find one, so backup pruning is done inside `pushProgress`.
- The merge rules in 2.6 are my reading of the save's shape from `save.js` and `actions.js`. Someone who knows
  the game's balance might want different rules for stars.
- The 3-picture secret, the 2-second push delay, the limit of 20 backups and 8 children are judgement calls, not
  requirements.
