## 1. How the game works today

### What it is

**Le Gala de danse** (`app/nodegx.project.json`, name "Le Gala de danse") is a management game in French and English. The child runs a dance school and prepares its end-of-year gala:

- the running order (Programme)
- each dance's formation and choreography, built from named blocks of steps
- the snacks (Goûter)
- costumes and hair
- the dressing-room furniture (La loge)
- the car park, which arrives in season 2
- a shop where stars buy things

Then they run a dress rehearsal, or try a single dance, and finally play gala night. Each evening is simulated by a rules engine and acted out in a 3D school (three.js).

The gala earns **stars**, and a **notebook** keeps a record of each season's gala. "Next season" brings new classes: the teenagers, then the mums. One gala can be played per season (`galaDone`).

There is also a **grown-ups' page** behind the ⚙︎ chip. On it, a signed-in grown-up can rename steps and costumes, change prices and the starting stars, and add new steps and costumes. Those changes are saved on a backend and laid over the game's tables for everyone who plays.

### How it is put together

Rules files are never edited in `app/`. |

| `app/scripts/game/*.js` | What a press does (`actions.js`, `dispatch.js`), the save's shape (`save.js`) and words (`text.js`). |
| `app/scripts/view/*.js` | Pure functions that turn the save plus the screen state into what each panel shows. |
| `app/scripts/settings/*.js` | The grown-ups' checker (`check.js`, generated from `tools/check.src.js` by `tools/sync-check.mjs`) and `apply.js`. |

Script files are CommonJS-like: `use('rules/data')`, `exports`. JavaScript Function nodes load them by listing them in their `uses` parameter and call them as `Scripts.<file>.<fn>`.

### How a visit runs

1. **`App`**: a Router (start page `/Pages/Game`, plus `/Pages/Grownups`) and one **`Logic/Start Up`** component.
2. **`Logic/Start Up`** does the following, in this order:
   - `su_words`: a Static Data node holding every game sentence as `{key, fr, en}`, put in the Variable `words`.
   - `su_gala`: a **persisted Global Store `gala`** (`persist: true`, `storageKey: "gala-game-v2"`). **This is the save, kept on this device.** It holds one key, `save`.
   - `su_ui`: a non-persisted Global Store `ui` (screen, tab, selection, the live evening `live`, results `res`, camera, toast).
   - `su_changes`: Query Records on `GameChange` (the grown-ups' changes). `su_wait` is a 4-second Timer so a missing backend doesn't hold up the game. `su_apply` runs `settings/apply.applyOnce()` on whichever of the two answers first. It rechecks each row with `settings/check.toRows()`, then `rules/data.applyRows()` changes the rule tables in place, once per visit.
   - `su_open`: `game/save.mend(stored.save)`. It repairs or upgrades an older save and starts afresh from anything unreadable. `su_setSave` writes the result back to `gala.save`, then `su_setReady` sets the Variable `ready`.
3. **`Pages/Game`** mounts once `ready` is true. It contains `Game/Stage 3D`, `Game/Top Bar`, `Game/Camera Bar`, `Game/Sheet` (the tabs in `Tabs/*`, the live evening in `Game/Live`, the verdicts in `Game/Results`), `Game/Furniture Toolbar`, `Game/Toast` and `Game/Season Letter`, plus the **`Game/Dispatcher`**.

### The parts this feature touches, in detail

**The one place the save changes.** Every button sends an event on channel `gala-act` with `act` and `arg`. The 3D stage sends them too, through `s3_send`. In `Game/Dispatcher`, `dp_fn` calls `game/dispatch.dispatch(act, arg, save, ui, words, stage)`, which returns `{save, ui, toast}`. `dp_setSave` then writes the new save to `gala.save`.

Apart from `su_setSave` at start-up, **`dp_setSave` is the only writer of the save**. Every press that changes something rewrites the whole save on the device straight away. About 20 components *read* `gala.save` through `GlobalStore.Subscribe` (Top Bar, Sheet, every Tab, Season Letter, Results, Live, Camera Bar, Stage 3D through `Pages/Game`, and the Grownups page for the language).

**The save** (`app/scripts/game/save.js`) is one JSON object:

```
{ v: 2, lang, season, galaDone, seenIntro, sound, seed,
  plan:   { start, interval, order[], numbers{ P1..F1: {A, B, blocks[], chain[], costume} }, hair{}, snack,
            cakeG, bottles, crepes, compotes, parking{width, doors}, backdrop },
  school: { name, logeCols, stars, earned, owned{}, upgrades{}, furniture[] },
  notebook: [ { season, at, points, satisfaction, nums{} } ] }
```

I measured it with the game's own `fresh()` and `nextSeason()`: about **3 KB** fresh and about **4 KB** at season 5. A long-played save with many blocks and furniture should stay well under 50 KB. That is small enough to send whole.

Other functions in `save.js` that matter here:

- `mend()` fills in anything a newer version added and **keeps extra fields it doesn't know about**. I'll rely on that.
- `nextSeason()` and `fresh()` are the other two whole-save transitions:
  - `fresh()` is reached from the notebook's "Start again" (`note:resetYes` in `dispatch.js`, buttons in `Tabs/Notebook`).
  - `nextSeason()` is reached from `go:nextSeason`.
- `fromRound1()` (importing an older "round 1" save) **is not called from anywhere**.

**Gala results.** `actions.finishGala()` adds the points to `school.stars` and `school.earned`, sets `galaDone`, and adds a notebook entry. It runs only on `runDone` for a gala. The evening in progress (`ui.live`, `ui.res`) is in the non-persisted `ui` store, so a reload mid-evening loses the evening, not the save. Two things also matter for syncing:

- `Stage 3D`'s `beginRun()` works from the save as it was when the run began.
- `s3_sync` calls `stage.sync(save, ui)` every time the save changes.

**Things that are per-device today but would follow a child:** `lang` and `sound` live inside the save, so they'll travel with the child. That seems right.

**Grown-ups today: one "home" per backend.**

- `app/nodegx.security.json` sets `signup: "public"`.
- The `GameChange` collection is readable by anyone (`find/get: public`) and writable by nobody directly.
- Functions `saveChange` and `removeChange` require `role:grownup`. `claimGrownup` only requires being signed in.
- In `Pages/Grownups`, Log In or Sign Up is followed by `claimGrownup`. That function (`__cloud__/claimGrownup`) puts the caller in role `grownup` **only if nobody holds that role yet**. So the first account ever is *the* grown-up of the whole backend, and every other account, a child's included, is refused.
- `saveChange` reloads the existing rows, runs the same `checkChange()` the browser uses (a hand-pasted copy of `tools/check.cloud.js` plus `tools/cloud-save.glue.js`; I checked that they match), then creates or updates one `GameChange` row `{table, rowId, fields}`.
- New steps and costumes get ids like `pas<time36>` and `tenue<time36>` (`view/grownups.js`), and a save can refer to them.

**What is not there at all:** no idea of who is playing, one save per browser, no account for children, nothing kept on the server about a game, and no handling of being offline. The game is fully playable with no network once the page has loaded: the rules, 3D and save all live in the browser. The only network calls are the `GameChange` read at start-up and the grown-ups' page.

## 2. The plan

### 2.1 Decisions

1. **The backend is shared by families, so it must be put online.** "The family tablet and a laptop at school" means the backend has to be reachable over HTTPS from anywhere. Today it's `127.0.0.1:8585`. Once it's online, it serves more than one family. So **"the grown-up" becomes "a grown-up of a family"**, and the grown-ups' game settings (`GameChange`) become **per family**. If they stayed global, the first grown-up to sign up would control every family's game.
2. **Children have accounts the grown-up creates; they never sign up.**
   - A child is a backend user made server-side by the grown-up (NodeGX's Create User node, which mints no session).
   - The child has no email and no username of their own: the username is generated and never shown.
   - The child signs in with three things: the **family code** (three easy words, e.g. `lune-tutu-nuage`, given out by the grown-up), **tapping their picture**, and a **4-digit secret code** (PIN).
3. **The device always plays a local save; the server keeps a copy.**
   - Play never waits for the network. Every press is saved on the device first, exactly as now, and then sent to the server in the background.
   - The server keeps one current save per child, with a revision number, and older copies as backups.
4. **Nothing is ever thrown away by the sync.**
   - When two copies disagree (the same child played offline on two devices), the game keeps the one that is **further along** as the current save. The other becomes a backup a grown-up can restore.
   - Saves are never merged field by field: a choreography half from one device and half from another would be nonsense.
5. **The guest game stays as it is.** Someone who never signs in plays exactly as today, in the same on-device save.

### 2.2 What is stored on the server

All new collections are **closed to the browser** (`nobody` for find, get, create, update and delete in `nodegx.security.json`). They are only reached through the cloud functions in 2.4, which check who is calling. That way none of this depends on row-level rules I haven't confirmed NodeGX has.

| Collection | Fields | Notes |
|---|---|---|
| `Family` | `code` (unique), `name` (optional), `createdBy`, `createdAt` | `code` is 3 words from a kid-safe list plus a check digit, e.g. `lune-tutu-nuage-4`. It can be renewed by the grown-up. |
| `_User` (built-in) | add `kind` (`grownup` \| `child`), `family`, `nickname`, `avatar` | Children: `username = c_<random>`, password random and long (see 2.5). Grown-ups: username and password as today, email optional (for password reset). |
| `ChildKey` | `child` (unique), `family`, `pinHash`, `pinSalt`, `failed`, `lockedUntil` | Kept apart from `_User` so it can never be read with a user. PIN hashed with SHA-256 and a per-child salt (the Hash node). The real protection for a 4-digit code is the lock-out, not the hash. |
| `ChildSave` | `child` (unique), `family`, `rev` (integer), `save` (JSON string), `hash`, `season`, `stars`, `galaDone`, `schoolName`, `updatedAt`, `device` | The current save. The summary fields are for the grown-ups' overview, so the grown-up doesn't have to read save JSON. |
| `SaveBackup` | `child`, `family`, `rev`, `save`, `reason` (`conflict`, `reset`, `adopt`, `restore`, `daily`), `createdAt`, `device` | The last 20 per child plus one per day for 30 days. Pruned by `pushSave` itself, so no scheduled job is needed. |
| `GameChange` (exists) | add `family` | Every existing row is stamped with the first family during the migration (2.9). |

Roles: keep `grownup` and add `child`. The role is created once at setup; Add User To Role is used with `createRole` off, so a typo fails visibly.

### 2.3 What is stored on the device

The persisted Global Store `gala` (storage key `gala-game-v2`) stays where it is, and `save` keeps meaning "the save being played now". That way none of the ~20 components that read `gala.save` change. It gains four keys:

| Key | What it holds |
|---|---|
| `save` (exists) | The save being played. It gains one field, **`owner`**: `"guest"` or a child's user id. |
| `slots` | `{ guest: save, <childId>: save, … }`: the saves of profiles **not** being played right now. |
| `profiles` | `{ deviceId, familyCode, children: [{id, nickname, avatar, pinCheck}], last }`. These are the children known on this device. `pinCheck` is a salted PBKDF2 hash used only to switch profile offline. |
| `sync` | `{ <childId>: { rev, pushedHash, lastSyncAt, note } }`: the server revision this device's copy is based on, and the hash of what was last sent. |
| `settingsCache` | The last `GameChange` rows fetched for this device's family, so a game started offline still has the family's custom steps and costumes (see 2.7). |

There are three design points here:

- **`owner` inside the save is the source of truth for whose save is on screen.** Switching profiles takes several store writes (`slots[current] = save`, then `save = slots[target]`). If the tab dies between two writes, start-up reads `save.owner` and puts things right: no save ends up under the wrong child. Each step only ever duplicates a save, never removes one, until the final step.
- **"Not yet sent" is not a flag that can be lost.** A save needs sending when `hash(save) ≠ sync[owner].pushedHash`. That is recomputed at start-up, so a crash between "saved on device" and "sent" just means it gets sent next time.
- An existing save with no `owner` is a guest save: `mend()` sets `owner: "guest"`. Nobody's progress moves when this ships.

### 2.4 Cloud functions (server-side workflows)

| Function | Who may call | What it does |
|---|---|---|
| `createFamily` | authenticated, not yet in a family | Creates `Family` with a fresh code, sets the caller's `kind=grownup` and `family`, and adds them to role `grownup`. **Replaces `claimGrownup`** for new grown-ups. |
| `addChild` | `role:grownup` | Takes `nickname, avatar, pin`. Checks the nickname with the existing `cleanName()`/`rude()` from `tools/check.src.js`, and that it is unique in the family. Then: Create User (`c_<random>`, random password, `kind=child`, `family`) → Add User To Role `child` → `ChildKey` → an empty `ChildSave` with `rev 0`. |
| `updateChild` | `role:grownup`, same family | Rename, change picture, set a new PIN, unlock after too many wrong codes. |
| `removeChild` | `role:grownup`, same family | Deletes `ChildSave`, `SaveBackup`, `ChildKey`, then the user with Delete User, which removes their sessions first. This is the "delete my child's data" answer. |
| `familyOverview` | `role:grownup` | Each child's nickname, picture, season, stars, last played, last device, and backups. |
| `restoreBackup` | `role:grownup`, same family | Makes a backup the current save as `rev+1`. The save it replaces becomes a backup first. |
| `linkDevice` | `role:grownup` | Returns the family code and children list, so the grown-up can set up a device in one tap. |
| `findFamily` | public | Takes a family code and returns `[{id, nickname, avatar}]` (nothing else). Slowed down after wrong codes (2.10). |
| `childSignIn` | public | Takes `familyCode, childId, pin`. Checks `ChildKey` with lock-out (5 wrong codes → locked 15 minutes, and the grown-up sees it). On success, signs the child in (mechanism: 2.5). |
| `getSave` | `role:child` | Takes `knownRev`. Returns `{same: true}` or `{rev, save}` for **the caller's own** save. The child id always comes from the session, never from a parameter. |
| `pushSave` | `role:child` | Takes `save, baseRev, hash, deviceId, reason`. Checks the save is JSON, `v === 2`, under 64 KB, and has `plan`/`school`. Then:<br>• If `baseRev === rev`: store it as `rev+1` and return `{rev}`.<br>• Otherwise: return `{conflict, rev, save}` and store nothing.<br>• With `reason: "reset"` or `"adopt"`, or when the client resolved a conflict, the save being replaced is written to `SaveBackup` first.<br>• Prunes backups. Sending the same `hash` twice is a no-op, so a retry after a dropped answer is harmless. |
| `familySettings` | public | Takes a family code (or the caller's family) and returns that family's `GameChange` rows. Replaces the public read of `GameChange`. |
| `saveChange`, `removeChange` (exist) | `role:grownup` | Same checks as today, plus a **filter and stamp on the caller's `family`**, so one family can't change another's game. |
| `claimGrownup` (exists) | — | Turned into the one-off migration `adoptHome` (2.9), then retired. |

All functions that can fail return `failure` with a short reason key, like the existing ones do (`gm_<reason>` words), so the page can explain the problem in the child's language.

### 2.5 How a child signs in

**First the grown-up sets things up** (Pages/Grownups, the ⚙︎ chip):

1. Sign up or log in, as today (email optional, recommended for password reset).
2. "Create our family" (`createFamily`). The family code is shown, with a "copy" button and a printable card.
3. "Add a child": nickname (not a full name), a picture (the `starter-imagery` avatars `avatar-1..6`, or an emoji), and a 4-digit code the grown-up picks or the game suggests (`addChild`).
4. Optional: "Use this device for our family" (`linkDevice`). The tablet then remembers the family code. A child on it never has to type the code, and guests on it see the family's custom steps and costumes.

**A child on a new device** (the school laptop), from a **"Who's playing?"** chip in the Top Bar:

1. Choose "I have an account", then type the family code (`findFamily`).
2. Tap their picture, then type their 4-digit code (`childSignIn`).
3. The game fetches their save (`getSave`) and they carry on where they left off. The device remembers the family and the child for next time.

**A child on a device that knows them:** "Who's playing?" shows the pictures (plus "Guest"). Tapping your own picture asks for your code, unless you're already the one signed in.

**Two children sharing one device:**

- Each child has their own slot in `gala.slots`, and the guest has one too.
- Switching does three things:
  1. Send the current child's unsent changes. If that fails, they stay marked unsent on the device; switching never waits on the network.
  2. Log Out.
  3. Sign the other child in, then swap the saves (2.3).
- Only one backend session exists at a time. When signed in to a profile, the Top Bar always shows that child's picture and name, so nobody plays in their sibling's school by accident.

**Switching offline:** the PIN is checked against `profiles.children[].pinCheck`, which is stored at the last successful online sign-in. That child's changes stay unsent until their next online sign-in, and the chip says so.

**Signing out on a shared computer:** "Sign out and forget me on this computer" sends the save first. If sending fails, it warns ("your last changes are only on this computer") rather than deleting them. Then it removes the slot and the profile. Plain "Sign out" keeps the slot.

**How `childSignIn` actually creates a session.** This is the one mechanism I couldn't confirm without opening the project's backend tools (part 4). In order of preference:

- **(a)** NodeGX can mint a session for a given user server-side. Then `childSignIn` returns a session token, and the page becomes that user.
- **(b)** Otherwise, `childSignIn` sets a fresh random one-time password on the child's account (Update User, server-side) and returns `{username, password}`. The page passes them straight to the existing Log In node. The child never sees either. *Check:* does changing the password end the child's sessions on their other devices? If it does, that's acceptable: those devices simply ask for the code again next time they sync, and nothing is lost.
- **(c)** Last resort: the child's real password is derived from the family code plus the PIN, and Log In is used directly. This depends on the backend's own rate limiting for protection against guessing, and it should only be chosen if that limiting exists.

### 2.6 What happens to progress already on the device

**When this ships:** the existing save in `gala-game-v2` is opened by `mend()`, given `owner: "guest"`, and keeps being played exactly as today.

**A child's first sign-in on a device that has a guest game with progress** ("progress" means season > 1, or a notebook entry, or `earned > 0`, or the school was renamed). There are three cases:

| The child's server save | What happens |
|---|---|
| empty (new account, `rev 0`) | Ask: *"Keep playing with this school? (Season 2, 85 ⭐, 'Les Étoiles')"* → **Yes** (default): the guest save is copied into the child's slot and sent with `reason: "adopt"`. → **No**: the child starts afresh. |
| has progress | Show both schools side by side (name, season, stars) and let the child pick. The one not picked is sent as a `SaveBackup` (`reason: "adopt"`), so a grown-up can bring it back. |
| identical (same hash) | Nothing to ask. |

In every case **the guest slot itself is left untouched on the device.** Adopting copies the save; it never moves it. A sibling or a visitor who plays as guest still finds that game.

### 2.7 What happens offline, and when the connection drops mid-game

- **During play:** nothing changes from today. Every press is written to the device by `dp_setSave` before anything else happens, and no game action needs the network. A dropped connection mid-gala loses nothing. The gala's result is written to the save on `runDone`, locally, and sent when possible.
- **Sending:** a new **`Logic/Cloud Save`** component (2.8) watches `gala.save`. When the owner is a child and the save differs from what was last sent, it sends:
  - 3 seconds after the last change (debounced, like the "autosave after typing" pattern);
  - **immediately** after a gala, a new season, or a reset;
  - when the page is being hidden or closed (`visibilitychange`/`pagehide`);
  - when the browser says it's back online;
  - otherwise, retries with growing gaps (5 s, 15 s, 1 min, then every 5 min).

  Every send is idempotent (same `hash` = no-op), so a send whose answer was lost is simply sent again.
- **Fetching:** on sign-in, at start-up, and when the tab comes back to the front after more than a minute, `getSave` checks for a newer revision. A newer server save is **never swapped in during a run or on the results screen** (`ui.screen` `run` or `results`). It waits until the child is back on the preparation screen. Swapping it in mid-evening would pull the plan out from under the 3D stage.
- **Two copies disagree** (`pushSave` says conflict, or `getSave` brings a newer revision while this device has unsent changes). A pure function `reconcile(local, server)` decides:
  1. Same hash: just take the server's `rev`.
  2. Otherwise keep the one that is **further along**, compared in this order: `season`, then `galaDone`, then `notebook.length`, then `school.earned`; on a tie, the most recently changed.
  3. The other copy becomes a `SaveBackup` with `reason: "conflict"`.
  4. If the device's copy lost, a toast tells the child: *"Your game from another device was further along, so we opened that one. Your grown-up can bring back this one."*

  The order puts progress before recency for a reason: `finishGala` adds stars once per season (`galaDone`), and "most recent wins" could throw away a gala the child played on the other device.
- **The session runs out while offline:** play continues, and the save stays unsent on the device. The chip asks for the code again when online, and the save is sent after sign-in.
- **Starting the game with no connection:** today `su_wait` fires after 4 s and the game starts with the default tables. That breaks a save whose dance uses a grown-up's custom step (`pas…` id). Start Up will use `gala.settingsCache` when `familySettings` doesn't answer, and refresh the cache when it does.
- **Visible but calm status:** a small cloud mark next to the child's picture in the Top Bar shows one of three states: ☁️✓ saved, ☁️… waiting to send, ☁️✕ offline – saved on this device. It never blocks play.
- **Not covered by this feature:** *reloading* the page while offline needs the app itself to be cached by the browser (a service worker). I don't know whether NodeGX's published app does that (part 4). If it doesn't, the game can't be opened offline, but nothing already saved on the device is lost.

### 2.10 What could go wrong

| Risk | What I'd do about it |
|---|---|
| **No server-side way to sign a child in** (2.5 a/b unavailable) | Fall back to 2.5 c only if the backend limits login attempts. Otherwise use a 6-digit code or a picture code (3 pictures in order out of 12). Decide in step 0, before anything else is built. |
| **Guessing a 4-digit code** | Lock-out on `ChildKey` after 5 tries, shown to the grown-up. `findFamily` is slowed after wrong codes. The family code alone reveals only nicknames and pictures, which is why the plan asks for nicknames, not full names. |
| **A child signs up as a "grown-up" and makes a family** | It can't reach anyone else's family or settings, so the harm is contained. A real grown-up check (email confirmation) could come later. |
| **Children's data and privacy** (the game is French, so GDPR applies; parental consent below 15) | The grown-up creates the account, which is consent given by the grown-up. Store as little as possible: nickname, picture, PIN hash, saves. No email for children. `removeChild` deletes everything. Write a short privacy note for the Grownups page. **Needs a human decision** on where the backend is hosted (EU). |
| **A swap during a gala desyncs the 3D stage** | `canSwapNow(ui)`: never swap during `run` or `results`. |
| **Double-counting a gala** played on two devices | No merging; keep the further save; the other goes to backups. |
| **A crash in the middle of a profile switch** | `owner` inside the save; writes are ordered so they only duplicate (2.3). |
| **localStorage cleared** (school computers often clear on log-off) | The server copy is the safety net. Whatever wasn't sent yet is lost; the cloud mark makes "waiting to send" visible. Send immediately after galas and seasons. |
| **localStorage full or blocked** (private browsing) | Each save is ~4 KB, so this is unlikely. Catch the write failure and tell the child their game is only saved online on this device. |
| **Saves referring to a family's custom steps** on a device not linked to that family | `familySettings` is read for the *signed-in child's* family, then cached. `mend()` already drops unknown numbers. Check what the engine does with an unknown move id, and make it skip it rather than fail. |
| **The grown-ups' `GameChange` now depends on the family** | A guest on an unlinked device gets the default game. That's a change from today, where every device on the home backend saw the home's settings, and it's intentional. |
| **Moving the backend online** | Today it's `127.0.0.1`. School networks may block unusual hosts. It needs HTTPS, backups of the database, and someone to run it. This is the biggest piece of non-code work in the plan. |
| **Save format changes later** (`v: 3`) | `pushSave` stores `v`. A device with an older game version must not overwrite a newer save: `pushSave` refuses a lower `v` than the stored one and the app asks for a reload. |

## 3. How we'll know it works

**Automated, in node** (in the same style as `tools/check-views.mjs` and `gala-rules/tests`):

- `profiles.js`:
  - switching between guest, A and B keeps all three saves byte-identical;
  - stopping after any one write of a switch, then running start-up's repair, loses nothing and shows the right owner;
  - a save with no `owner` becomes the guest's.
- `sync.js` `reconcile()`, as a table of cases: identical; local ahead; server ahead; same season but only one has played its gala; equal progress with different times. In every case, both copies end up either current or in a backup.
- `hashOf()` gives the same hash for the same save regardless of key order.
- The existing checks still pass: `node --test gala-rules/tests/*.test.mjs` (19 pass today), `node tools/check-rules.mjs`, `node tools/check-views.mjs`.

**Cloud functions** (called with test accounts through the `nodegx` server):

- A child cannot:
  - call `saveChange`, `addChild` or `familyOverview`;
  - read or write another child's save, since the child id always comes from the session.
- A grown-up of family A cannot see or change family B's children, saves or settings.
- 5 wrong codes lock `childSignIn`. The right code during a lock-out is still refused. "Unlock" works.
- `pushSave`:
  - a stale `baseRev` answers conflict and stores nothing;
  - the same `hash` twice makes one revision;
  - a reset or adopt makes a backup;
  - more than 20 backups are pruned;
  - a 200 KB save or `v: 1` is refused.
- `removeChild` leaves no `ChildSave`, `SaveBackup`, `ChildKey` or session behind.
- `adoptHome` on an empty backend and on one with `GameChange` rows.

**Played, the way a person arrives** (`drive_page` from the start page, and by hand with two browsers standing in for two devices):

1. **Guest, unchanged:** a fresh browser plays as today. An existing `gala-game-v2` save from the current version opens with its school, stars and notebook intact.
2. **Set-up:** the grown-up signs up, creates the family, adds Léa and Sam, and gets the code.
3. **Keep the guest progress:** on a browser with a season-2 guest game, Léa signs in for the first time and chooses "keep". Her overview on the Grownups page shows season 2. The guest game is still there.
4. **Another device:** Léa signs in on a second browser with the family code, her picture and her PIN. She finds the same school, stars, choreography blocks and notebook.
5. **Sharing one device:** Léa plays, then Sam takes the tablet and plays, then Léa again. Neither sees the other's changes, and both are on the server.
6. **Offline mid-game:** stop the backend (or turn the network off) in the middle of preparing, then during a gala. Play on, finish the gala, go to the next season, close the tab. Reopen with no network: everything is there, and the cloud mark says "waiting". Turn the network back on: it is sent with no action from the child, and the other browser shows it.
7. **Played offline on both:** Léa plays offline on both browsers, getting further on one. When both reconnect, the further one wins on both, a toast explains it, and the grown-up sees the other as a backup and can restore it.
8. **Session gone while away:** expire Léa's session. Play continues, she's asked for her code, then it sends.
9. **Forget me at school:** "Sign out and forget me" with unsent changes and no network warns her. With network, it sends, then removes her from that computer.
10. **Starting offline with the family's custom step** in a dance: the game still opens and plays that dance.

**Done means** all of the above pass, plus a week on the real family tablet and a real school laptop with nothing lost. Every sync conflict should be visible in `SaveBackup`, so a week with no unexpected backups is also a signal.

## 4. How I found my way around

**Easy to understand:**

- The script files are short and very well commented. Each says what it is and where it came from (e.g. `save.js`: *"Where it is kept is the graph's business: the persisted Global Store "gala" holds it under the key "save""*).
- Component `description` fields and node labels are written in plain sentences ("Don't wait for the backend for ever", "Only the first account may claim"). With a small script that prints each graph as an indented tree with its wires, `Logic/Start Up`, `Game/Dispatcher` and the cloud functions read almost like prose.
- The architecture is disciplined:
  - one event channel (`gala-act`);
  - one pure `dispatch()`;
  - one writer of the save;
  - views as pure functions;
  - rules kept in a separate tested package and copied in by tools.

  That is why the plan can add profiles and sync almost entirely *around* the game rather than inside it.

**Hard, or not possible from here:**

- The graphs are JSON with generated port names (`out-save`, `in-rows`, `itemOutputSignal-save`). Reading the bigger pages (`Pages/Grownups`, `Game/Sheet`, the tabs) by wire takes patience. I read the ones this feature touches in full and the rest only for who reads `gala.save`.
- **`reference/src/` is missing.** `tools/sync-stage.mjs` and `tools/extract-words.mjs` read from it, so the 3D stage and the words can't be regenerated from source in this folder. That's not a problem for this feature (it doesn't touch the stage), but it's worth knowing.
- **I did not open the project with the `nodegx` server** or run the app. Opening it binds the server to the project and, judging by `app/.gitignore`, writes a machine-specific file into `app/`. You asked that PLAN.md be the only file written. So I read the files directly, and learned NodeGX's backend features only from the server's read-only example library. That library describes Create User, Add User To Role, Update User, Delete User, Get User Roles, Verify Session Token, Secrets, Hash, Query/Create Records with Upsert, and Optimistic Update.
- **I can't see the backend's database.** I don't know whether the current home has a grown-up and saved `GameChange` rows, so the migration in 2.9 is written to be safe either way.

**Where I'm unsure of what I wrote:**

1. **How a child's session is created** (2.5 a/b/c). This is the biggest unknown and the first thing to settle. The rest of the plan doesn't depend on which option wins.
2. **What `persist: true` on a Global Store does exactly.** I assume browser `localStorage`, the whole store as one value, written synchronously on each Set. If writes are deferred, "every press is saved on the device first" needs checking against a tab closed right after a press.
3. **Whether `nodegx.security.json` can express "only your own rows"** (`creatorOwns` suggests something like it). I avoided relying on it by closing the new collections and going through cloud functions. That costs a few more functions but is easy to reason about.
4. **Rate limiting and hosting.** I don't know what the backend offers for limiting login attempts, or how NodeGX deploys it online. Both affect 2.5 and 2.10.
5. **Offline reload.** Whether the published app can be opened with no connection at all (part 2.7, last point).
6. **The "further along" order** (`season`, then `galaDone`, then notebook length, then stars earned) is my judgement of what a child would call "further". It's worth a look by whoever knows the game's design. Because the other copy is always kept as a backup, getting it wrong costs a grown-up's restore, not lost progress.
7. **Making grown-up settings per family** is a change to today's behaviour that I decided on (2.1) because the backend has to go online. If the plan is instead one private backend per family, `Family` and the scoping can be dropped, and the rest stands.
