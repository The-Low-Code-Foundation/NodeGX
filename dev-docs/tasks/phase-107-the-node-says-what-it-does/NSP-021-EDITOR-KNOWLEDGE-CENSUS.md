# NSP-021 §3.1 — what the editor knows about a node, and where it learns it

**Written 2026-10-03 (P112 session 1) on `c25fb8ee5`, built once for NSP-021 and P112 OWN-000 §3.3; both cite this file.**
A research pass over the editor, the runtime, the viewer, the catalog and the MCP server; every line number was read in
the file it names. Three citations were re-read by the session that filed it (`nodelibraryexport.ts:217`,
`editorconnection.ts:898`, `NodeGraphEditorNode.ts:580`) and the three dead-path claims in §3 were re-checked by grep;

## 1. The pipe most rows depend on

The editor's node library comes **from the runtime, over the viewer socket**, not from a file:

1. `noodl-runtime/src/nodelibraryexport.ts:217` `generateNodeLibrary` walks `nodeRegister._constructors[*].metadata`.
2. `noodl-runtime/noodl-runtime.ts:782` `getNodeLibrary` adds `projectsettings` and `modulefailures`; `:815` `sendNodeLibrary`.
3. `noodl-runtime/src/editorconnection.ts:898-905` sends `{cmd: 'nodelibrary'}`.
4. `ed/ViewerConnection.ts:331` → `loadNodeLibrary` `:727` → `ed/models/nodelibrary/NodeLibraryImporter.ts:277` `onClientImport`,
   which merges clients and sets `window.NodeLibraryData`, then `NodeLibrary.instance.reload()` (`:461-472`).
5. `ed/models/nodelibrary/nodelibrary.ts:86` `loadLibrary` wraps every entry in `new BasicNodeType(type)` (`:109`);
   `BasicNodeType.ts:57-59` copies every field as-is.
6. `NodeGraphNode.type` (`ed/models/nodegraphmodel/NodeGraphNode.ts:103-110`) resolves by name, else `getUnknownNodeType`.

Three more producers feed the same importer: the **cloud types** from the static `ed/models/nodelibrary/cloud-node-library.json`
(merged at `NodeLibraryImporter.ts:294-301`; generated by `scripts/cloud-node-library/generate.js`); the **workflow step
kinds** from `ed/models/workflow/workflowNodeLibrary.ts:384-400` (ports, colour and category hand-written there, from the
backend's `GET /admin/workflow-step-kinds`); and **per-instance dynamic ports** on a second message, `{cmd: 'instanceports'}`
(`noodl-runtime/src/editorconnection.ts:720-776` `sendDynamicPorts`, received at `ed/ViewerConnection.ts:245-249` →
`NodeGraphNode.setDynamicPorts` `:883`; 43 runtime and viewer files call `sendDynamicPorts`).

**The catalog** (`noodl-types/src/node-catalog.json`, `-enriched.json`) is read by `ed/validation/catalog.ts:51,69` and
`ed/validation/enrichedCatalog.ts:40`. It is generated by `scripts/node-catalog/generate.js`, whose extractor calls the
same `generateNodeLibrary` (`scripts/node-catalog/extractor-entry.js:18,102`) and then **re-derives** the per-node fields in
`scripts/node-catalog/lib/build-catalog.js:204-255`.

**`@nodegx/node-spec` is read by nothing in the editor or the MCP server.** Its importers are tests
(`noodl-runtime/test/node-spec/*`, `nodegx-export/tests/*`) and `scripts/bugs.js`. That is the gap NSP-018, NSP-020 and
NSP-021 close, and the reason P112's prototypes had to reach into source.

## 3. Dead paths and holes (each re-checked by grep on 2026-10-03)

- **`type.visual` / `type.canHaveVisualChildren`** (`NodeGraphEditorNode.ts:580-585`): no producer in the runtime, the viewer or the
  editor sets them; nothing calls `NodeGraphEditorNode.isVisual()`.
- **`type.allowSingleInstanceOnly`** (`NodeGraphNode.ts:1032`): no producer. The runtime exports `singleton`, which the delete and
  copy rules read (`:655,659`), so **the `node-singleton` warning can never fire**. Filed as a bug (P107 ledger).
- **`shortDocs`, `searchTags`, `docs` on the runtime payload:** `shortDocs` is declared (`ed/types/nodeTypes.ts:16`) with no reader;
  `searchTags` is read only by `NodePicker.search.ts:201`; docs prose now comes entirely from the catalog.
- **`library.dynamicports`** (top-level managers): the reading code is commented out (`nodelibrary.ts:112-125`); the runtime still
  sends it (`nodelibraryexport.ts:299-308`).
- **`inNodePicker`:** the editor never reads it; the picker uses `nodeIndex` plus `getCreateStatus`. Only the catalog and AI code use it.
- `displayNodeName`: `BasicNodeType.ts:7` declares it with "TODO: Where is this from?". It comes from `nodelibraryexport.ts:431`.
- Not traced: every `NodeTypeAdapter`'s port list against its runtime twin, line by line; `ed/models/AiAssistant/*` (catalog-sourced
  throughout: `ContextBuilder.ts:223,253`, `explain/assemble.ts:24`).

## 4. What this says for NSP-021 §3.2 and for P112

Counting the "copied elsewhere" column: **every** type-level question has at least two answers today (runtime payload and
catalog), the child/parent rule has three, and connection validity has five. The spec package answers none of them yet
for the editor. The order NSP-018 → NSP-020 → NSP-021 is the order of this table's rows: names and descriptions first,
ports second, the rules (typecasts, allowAsChild, inspect) last. For P112, the rows a home-made editor hits first are the
picker list, the display names, the ports and the typecasts; OWN-001 and OWN-002 give it the format and the spec, and this
table says what it still has to take from the catalog until P107's three tasks land.
