DeepSeek V4.1 Flash, building a family app in Cline with the kit, knew that each family must see only its own
children. It set out to filter its Query Records on the server by `ownerId`, and couldn't find out how:

- `get_node_type DbCollection2` with `detail: "full"` and `ports: ["querySettings", …]` answered `notFound` for the
  filter. The catalogue entry has `inputs: []` and says the filter ports "are generated by the editor from the visual
  query (QueryRecordsAdapter)".
- `list_examples` ("filter the query on the server owner isolation") offered only `cloud-filter-records-tabs`, which
  filters on the client.
- It then looked outside its folder for the server's source (`grep -rl querySettings /Users/Shared`, `ls
  /Users/richardosborne/vscode_projects`; the lab's fence refused), and wrote: *"No filter shape documented. I'll
  discover it empirically at runtime."*

What it shipped: every Query Records fetches the whole collection, and two `JavaScriptFunction` nodes drop other
families' rows (`rows.filter(r => r.ownerId === owner)`). Every family's children, answers and the parent's PIN reach
every family's browser. With the local backend's `devOpen` (P112-OWN023-DEVOPENREAD), the grader read and changed them
with another family's token or with none (T7, T8 failed). A plain-code arm given the same request wrote
`WHERE family_id = ?` on its server and passed both.

The shape exists and the project's own templates use it (e.g. `templates/nightbook/components/__cloud__/sealEnvelope`):
`"visualFilter": {"combinator": "and", "rules": [{"property": "objectId", "operator": "equal to", "input": "id"}]}`,
with the input port `qp-id`. An agent writing files just can't see it.

Fix, any of:
1. The catalogue and `get_node_type` describe Query Records' `visualFilter` (and `visualSort`, `storageLimit`): the
   rule shape, the operators, and that each `input` becomes a `qp-<name>` port. Ideally `validate_component` checks
   it too (an unknown key like `querySettings.filter` is refused with the real shape).
2. An example, `cloud-query-own-rows`: a signed-in user's records, filtered on the server by a wired `User` id.
3. The backend's own guidance: with `creatorOwns` enforced, the query needs no owner filter at all (see DEVOPENREAD).
